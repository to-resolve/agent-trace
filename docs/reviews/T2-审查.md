## 三、实现质量

**做对的地方**（值得点名，后续卡继续保持）：

1. **链式调度**（任意时刻只挂一个 timer）—— 这让 pause/resume/cancel 的泄漏面天然为零，比"发一排 timer 再逐个清"干净得多。
2. **`observedAt` 省略时取「计划发生时刻」而非 fire 时的墙上时钟** —— 这是本卡最关键的一个判断。若取墙上时钟，测试就会因定时器抖动而不稳定，Phase 2 换成真实 SSE 后更是无法复现。结果只依赖剧本与基准，可重复性是这个项目的命根子。
3. **`isScenarioEvent` 复用 `isAgentEvent`** 而不是复制一份校验逻辑 —— 避免两份校验规则日后漂移。用 dummy `time` 顶替 `timeOffset` 再走同一套校验，手法干净。
4. **归档时拷贝入档**（`{ ...event.span }`）—— 已吐给消费者的对象不被后续 `span.end` 污染。事件对象的可变性是流式系统最常见的隐性 bug 源，这里提前堵住了。

## 四、裁决 1 —— `Scenario` 类型：**修订 `02`，代码不动**

**执行者的提问**：`02` §9 写 `steps[].event: AgentEvent`，装不下 `04` 的 `timeOffset` 相对时间格式，是否回头修订 `02`？

**裁决：修订 `02`，`ScenarioEvent` 的实现保留、不回改。**

理由三条：

1. **相对偏移不是权宜之计，是剧本的必要条件。** 剧本要可重复运行、可跨机器移植、可写进仓库做版本对比——绝对时间戳三条全做不到。所以错误的是 `02` 把类型写成了绝对时间的 `AgentEvent`，而不是 `04` 用了相对偏移。
2. **`04` 是已落地的事实输入。** 改一份 JSON 的成本远低于改一份已经能跑通全链路的类型设计，何况 JSON 那份是对的。
3. **代码侧的抽象是对的。** `ScenarioEvent` 与 `AgentEvent` 分离，把"存储形式"和"运行时形式"切成两层，中间用 `resolveEvent` 换算——这个分层恰好也是 Phase 2 接真实 SSE 时要用的形状（真实流给的是绝对时间，不需要换算）。

**已据此修订 `02` §9**，固化三条约束：

- 剧本中**一切 number 时间字段都是相对 run 起点的偏移**（含 `run.start.startedAt`、`span.startedAt/endedAt`、`span.end.endedAt`）
- `entity.create` 的实体用 `timeOffset: { createdAtMs, observedAtMs? }` 替代 `time`，`observedAtMs` 省略时取该事件的计划发生时刻
- `run.snapshot` **不得出现在剧本里**（回放语义，不是剧本语义）—— 执行者这条判断正确，已写进契约

## 五、问题清单

| 严重度 | 问题 | 位置 | 处理要求 |
|---|---|---|---|
| **必修** | `pause()` 在 `onEvent` 回调内被调用会被**静默忽略** | `simulated.ts` `fire()` / `pause()` | 见下详解，进 T3b |
| 建议 | `runId` 写死在剧本里，同一剧本 `start()` 两次会覆盖归档 | `simulated.ts:74,87` | Phase 1 做"多运行对比"时改成运行时生成唯一 runId，现在不动 |
| 建议 | `resolveJsonModule` 使剧本 JSON 可被 import | `tsconfig.json` | 测试 import 剧本是合理的；但**禁止 `src/` 业务代码直接 import 剧本 JSON**，否则所有剧本都会打进产物。剧本变多后改 `fetch` 动态加载 |

### 必修项详解：`pause()` 在 `onEvent` 内失效

`fire()` 开头执行 `timer = null`，随后同步调用 `handlers.onEvent(event)`。若 handler 内部同步调用 `pause()`，会命中 `if (state !== 'running' || timer === null) return` 的第二个条件直接返回，**状态没变、timer 也没清**；`fire()` 返回前照常 `armTimer()` 排下一个事件，暂停彻底失效。

同一个根因还带出第二个边界：`cancel()` 在**最后一个事件**的 `onEvent` 内调用时，随后 `state = 'done'` 会覆盖 `'cancelled'` 并触发 `onDone()` —— 主动取消了却报告"正常结束"。

**为什么现在就要修**（不是可选项）：Phase 1 的「中断介入」功能，形态就是"跑到某个条件自动暂停"，触发点必然落在 `onEvent` 里。那时候再修，故障现象会伪装成"中断逻辑写错了"，排查成本高一个量级。

**修法要求**（具体做法由执行者定，但必须满足）：

- `pause()` / `cancel()` **只判断 `state`，不再把 `timer === null` 当作提前返回的条件**；先置状态，timer 非空再清理
- `fire()` 在 `armTimer()` **之前**补一次 `state !== 'running'` 检查
- 自然结束分支（`nextIndex >= steps.length`）**也要先判 `state`** 再置 `done` / 调 `onDone`

**补测试**：在 `onEvent` 回调内调用 `pause()`，之后 `advanceTimersByTime(10_000)` 不得再产生任何新事件，`resume()` 后能继续跑完。
