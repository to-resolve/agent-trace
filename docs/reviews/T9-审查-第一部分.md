## 3. 问题清单

### 🔴 必修 B1：`consumersIndex` 在 invert 后残留，导致索引单向膨胀

**机理**：`ingestSpan` 中 `consumersOf(graph, entityId).push(span.id)` 不记逆操作（注释称"纯缓存，invert 后由 `consumersOf` 惰性重建兜底"）。但该注释的推理有漏洞——**`invert` 回滚 `span.set(prev: null)` 时只做 `graph.spans.delete()`，索引里的 spanId 不会被移除，而索引并非"下次一定重建"**：`consumersOf` 只在 `consumersIndex.get(graph) === undefined` 时重建，原图的索引一直存在，永远命中。

```
Step 1  applyEvent(span.start A 消费 E1)  →  index['E1'] = ['A']
Step 2  invert(span.set{A, prev: null})   →  spans.delete('A')
                                             index['E1'] 仍是 ['A']   ← 残留
Step 3  applyEvent(span.start A 消费 E1)  →  consumersOf('E1').push('A')
                                             index['E1'] = ['A', 'A'] ← 膨胀
```

**后果**：

1. **索引单向膨胀，永不回收** —— 每次"回滚 + 前进"循环，同一 spanId 累积一次。用户反复拖时间轴（时间旅行**最核心的交互**）时线性增长：10k span 拖 100 次 → 索引从 1 万涨到 100 万条
2. **`addEdge` 被重复调用** —— `ingestEntity` 遍历 `consumersOf(entity.id)`，索引重复 N 次就调用 N 次 `addEdge`。幂等检查会拦住边的重复（功能仍正确），但每次都要付 O(该节点出边数) 的 `some()` 扫描

**为什么测试发现不了**：

- `snapshot()` 只比较 `CausalGraph` 的字段，`consumersIndex` 是 `build.ts` 模块级 `WeakMap`、**不在图对象上**，深比较看不见
- 压力回滚测试是**单向回滚**（`for (let c = checks.length - 1; c >= 0; c--)`，每次只往回退），**从不"回滚后再前进"**，恰好绕开了触发条件

**为什么现在必须修（而不是等出问题时再说）**：

§11.9 要求「10k 回溯 step 5000 < 200ms」。按 M4 全链路 6.77ms/事件估算，checkpoint 深拷贝 + 正向重放 200 步 ≈ **1.35s**，远超验收线。**这决定了第二部分必须走 invert 细粒度回退**（单步回退是 O(逆操作数)，微秒级），而不是纯 checkpoint 重放。而一旦 invert 进入主路径，往返操作就会发生，B1 必然触发。

**修复方向（设计裁决）**：**`invert` 时让索引整体失效，下次 `consumersOf` 惰性重建。** 不为缓存设计精确逆操作。

- 语义正确性：`consumersIndex` 是**可推导的纯缓存**（代码注释自己声明"内容完全可从 graph.spans 推导"）。为一个可随时重建的缓存维护精确逆操作，是让它付出不可变数据结构的代价——**"整体失效"才是缓存的正确语义**
- 契约一致性：缓存失效不属于"图状态恢复"，因此**不新增第五种 `InverseOp`**，§11.3 四类契约保持不变
- 成本可接受：惰性重建让"回滚后不重放"零成本；"回滚后重放"的重建成本 O(spans × inputs) 与重放本身同阶

**实现提示**（具体结构由执行者定）：`consumersIndex` 现为 `build.ts` 模块私有，`journal.ts` 访问不到。建议抽 `src/core/graph/consumers-index.ts` 独立模块，`build.ts` 与 `journal.ts` 都 import。注意 `build.ts → journal.ts` 目前是 **type-only import，不构成运行时循环**，抽取后仍无循环。

**验收**：补一条「回滚 + 重放」往返测试——回滚到某点后重新应用同一批事件，断言索引不膨胀。测试方法：往返 N 次后，对某 entityId 调 `consumersOf` 检查无重复项（需导出一个测试可见的查询入口，或经 `ingestEntity` 的 `addEdge` 调用次数间接断言）。

## 4. 设计层面的发现

### 4.1 "纯缓存"的免责声明是个陷阱

B1 的根因是 `ingestSpan` 里的注释：「消费方索引是纯缓存（可从 spans 推导），不记逆——invert 后由 `consumersOf` 惰性重建兜底」。

这句话**每一半都对，合起来错**：

- "可从 spans 推导" ✅ —— 所以理论上能重建
- "惰性重建兜底" ❌ —— 惰性只在 `get(graph) === undefined` 时触发，而原图的索引一直存在，**永远不重建**

这是"纯缓存"这个标签带来的思维盲区：一旦认定某物是缓存，就容易默认它"反正能重算"，从而跳过对生命周期的追问。**但缓存的正确性依赖失效时机，不只是可推导性。**

通用检查法：**对每个"纯缓存/纯派生"结构，问「它什么时候失效」，而不只是「它能不能重建」。**

### 4.2 测试覆盖的盲区形状：只测单向，不测往返

压力回滚测试很扎实（400 节点、4 个随机检查点、与从头回放逐字段比对），但它的形状是**单向**的——从尾往回滚，从不回滚后再前进。

而时间旅行 UI 的真实交互是**往返**（拖过去、拖回来、再拖过去）。**单向测试覆盖了"回滚正确性"，恰好绕开了"往返累积性"。**

这类盲区的通用检查法：**对每个状态机制，问「它被反复来回触发时会怎样」，而不只是「单次触发对不对」。**

### 4.3 验收线之间的张力浮出水面

§11.9 的「10k 回溯 step 5000 < 200ms」与 §11.5 的「checkpoint 间隔 200 + 正向重放」存在张力：按实测 6.77ms/事件算，重放 200 步 ≈ 1.35s，**纯 checkpoint 路径达不到验收线**。

这不是缺陷，是设计约束的正常暴露——它实际上在告诉我们 **invert 细粒度回退是必需的，不是可选的**。第二部分应据此设计混合策略（长距离跳跃走 checkpoint 深拷贝，短距离回退走 invert），而不是硬调 checkpoint 间隔去凑。

**这一点应写入第二部分卡面**：不要为了凑 200ms 而把 checkpoint 间隔调到不合理的密度。

### 4.4 关于"快照与回滚互相污染"的教训

材料决策点 4 记录：`snapshot()` 辅助函数首版捕获 `graph.edges` 数组引用，基准图持续生长污染了先拍的快照，导致回滚断言对着终态比（红）。

这个坑是"替换 vs mutate"重要性的又一实证——**引用被共享时，新旧状态会互相污染**。它和裁决 8 是同一个根因的两个表现：前者是产品代码的 mutate，后者是测试代码的引用共享。

已写进 `snapshot()` 函数注释，做得对。
