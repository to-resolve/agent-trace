## 二、算法正确性核查

**`computeLayering` 的边界论证，我独立推演过，成立**：

- 增量模式下每个节点要么在 `fixedLayer`（prev 有、未受影响），要么在 `affected`（图里有、prev 没有 → 兜底并入；或 dirty / 下游闭包）。两者并集覆盖全图，不存在「既非边界又未 seed 却被递归到」的缝隙
- 「环必然整体落在受影响集合内」的论证正确：环上任一节点 dirty，沿出边的下游闭包会把整条环收进来，因此「不受影响 → 受影响」的入边不可能是回边，边界层号直接引用是安全的
- 菱形汇合（memo 命中）与回边（onPath 命中）的区分与 `query.ts` 的 `traverse` 同构，两个文件对「环」的语义一致

**决策点裁决**：

1. **增量层内排序不跑 4 轮交替扫描（决策 1）——认可。** 交替上扫要求按下游重排上游层，会牵动必须逐字段不动的固定节点——与增量的硬约束直接冲突。单趟「上游已落位节点 y 中心均值」+ 层号升序处理，是正确约束下的正确取舍，且有收敛性测试兜底。
2. **边数组 O(E) 整体重建（决策 3）——事实成立，触发契约裁决**，见下节。
3. **两处兜底防御（决策 4）——认可。** 漏标 dirty 自动并入、清场后误用增量走重建，都不改变正确调用路径的行为，属于买保险不付利息。
4. **常量不与 render 共享（T5 决策 5，源头在本卡）——裁定执行者正确**，见 T5 审查。我的卡面写法与 `01` §4 分层规则冲突，按更高权威处理并上报，是标准动作。

## 三、契约裁决 5 —— `LayoutEdge` 增加端点标识（`02` §10 已修订）

**问题**：`LayoutEdge` 只有几何坐标（`from` / `to`）不带 `fromSpanId` / `toSpanId`，导致两个后果：

1. **增量边更新在现有契约下不可能**——无法识别哪条旧边对应哪条新边，只能整体重建。节点坐标是 O(受影响集合)，边却是 O(E)，「仅重算受影响子树」的简历叙事在边这一半上不成立。
2. **store 被迫用「下标对齐」做映射**——`traceStore.applyEdgeStates` 与 `buildBadges` 依赖「`graph.edges` 过滤后与 `layout.edges` 顺序一一对应」。今天对齐成立（两处用同一谓词、同一遍历顺序），但这是**跨三个文件的隐式耦合**：任何一方改过滤条件（比如渲染层决定不画自环边），高亮就会**静默落到错误的边上**——又是那类不报错只出错的 bug。

**裁决**：`02` §10 已修订——`LayoutEdge` 增加 `fromSpanId: SpanId` 与 `toSpanId: SpanId`。渲染层不读它们、零成本；store 改用标识定位边，下标耦合消灭。边级增量更新本身**不在 T6 做**——先加标识，T7 压测若显示 O(E) 边重建是瓶颈，再做边级增量（那时契约已就绪）。
