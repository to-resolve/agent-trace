## 1. 修复落实情况

### 1.1 索引修复（采纳 §3.6 给的修法）

`checkpoint.ts:179`：

```diff
- invert(session.graph, session.journal.ops[i] ?? [])
+ invert(session.graph, session.journal.ops[i - session.journalBase])
```

逐字采用第二部分审查给的修法。`i - journalBase` 把全局索引转换为 `ops` 的相对索引，越界时 `ops[length+]` 直接返回 `undefined`——在 §1.2 去掉 `?? []` 后变成显式 TypeError。

### 1.2 去掉 `?? []`（§4.1 的顺手落实）

第二部分审查 §4.1 的原则（编程错误应崩溃而非静默降级）在此落实。修复后不变量保证 `i - journalBase ∈ [0, ops.length)`，直接索引足够——保留 `?? []` 只剩"掩盖未来不变量被破坏"的负作用。

探针也证明：回退一行让 bug 回来，**这是"防御性写法掩盖 bug"的典型实证**。

注释里写明该原则的出处（§4.1），让下次有人想加回来之前先看清历史。

### 1.3 不变量注释修正（第 76 行）

原注释：

```
 * - journal.ops.length === applied；ops[i] 对应 events[i]
```

修正为：

```
 * - journal.ops.length === applied - journalBase；ops[k] 对应
 *   events[journalBase + k]（相对索引，T9 第二部分审查 B3：注释原写
 *   「ops[i] 对应 events[i]」是错的——它在 journalBase = 0 时与实现无法
 *   区分，正是索引错位 bug 的温床）
```

修正后注释既描述实际语义，也点明旧注释为何是温床——给未来读代码的人留个路标。

### 1.4 守卫测试（含前提断言）

`checkpoint.test.ts:186-197`：

```ts
it('大步前进到非 checkpoint 边界后小步回退（journalBase < applied 区间的 invert 路径）', () => {
  const session = createReplaySession(events)
  seekTo(session, 100)
  seekTo(session, 1950) // 非 200 倍数 ⟹ journalBase=1800 < applied=1950
  expect(session.journalBase).toBeLessThan(session.applied) // 前提断言
  expect(session.journal.ops.length).toBe(session.applied - session.journalBase) // 相对索引不变量
  seekTo(session, 1900) // 落在 [journalBase, applied) 内 ⟹ invert 路径
  expect(snapshot(session.graph)).toEqual(snapshot(replayFromScratch(events, 1900)))
  expect(session.applied).toBe(1900)
  expect(session.journal.ops.length).toBe(1900 - session.journalBase)
})
```

**前提断言 `journalBase < applied` 不可省**——这是第二部分审查 §3.7 明确要求的：否则路径改变时（譬如某次重构让大步前进总是落到 checkpoint 边界）测试会"静默失去意义"，**这正是此前 13 个测试全绿却带 bug 的根本原因**。

第二重断言 `ops.length === applied - journalBase` 直接把不变量写进测试——以后不变量被破坏，会立即红而不是悄悄错。

## 4. 设计层面的发现

### 4.1 注释即不变量：不变量错了，注释就是 bug 温床

T9 第二部分审查 §4.2 已经记过这一点，本轮 B3 是它的最有力实证：

- 注释写 `ops[i] 对应 events[i]`（全局索引）
- 实现是 `ops[k] 对应 events[journalBase + k]`（相对索引）
- 两者在 `journalBase = 0` 时**无法区分**

**这是隐式不变量的典型陷阱**：注释不是给当下读代码的人写的，是给未来的自己（或者其他 AI Agent）写的，**未来面对的测试条件可能与今天不同**。

修正后的注释显式写出"journalBase = 0 时与实现无法区分"的缘由——给"未来想知道为什么要这样写"的人留了一条线索。这是好注释的形态：**写反直觉处的缘由，而非描述与实现同形的废话**。

### 4.2 测试设计盲区的成因

T9 第二部分审查 §4.3 记录的"只测边界值"问题，本轮 B3 是它的实证。补充一个观察：

> B1、B2、B3 三个必修都是"测试全绿但实现错"——它们的共同形态是**测试用某一参数组合跑通后，实现就被认为是正确的**。

**但正确的实现必须在整个参数空间内一致**，而非在某个特定的参数点上碰巧对。**这类 bug 的测试设计原则**：

| 测试设计原则 | 反例（本项目已发生） |
|---|---|
| 对"区间"取边界**和内部**点 | B3：只测 200 的倍数 |
| 对"合并路径"取每条**独立**触发条件 | B1：压力测试只做单向回滚 |
| 对"缓存"问**何时失效**而非"何时存在" | B1：WeakMap 一直存在 ≠ 一直有效 |

这条原则已经写进 HANDOFF.md 第 5 节，新增的对应方法论可以**不必单独再提炼**，直接引用即可。
