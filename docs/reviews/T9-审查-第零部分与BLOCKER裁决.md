## 3. 裁决

### 裁决 8：采纳路线 A（`span.end` 改替换写入），不采纳路线 B

**采纳 A**：

```ts
case 'span.end': {
  const span = graph.spans.get(event.spanId)
  if (span === undefined) return graph
  graph.spans.set(event.spanId, {
    ...span,
    status: event.status,
    endedAt: event.endedAt,
    outputEntityIds: [...new Set([...span.outputEntityIds, ...event.outputEntityIds])],
    ...(event.error !== undefined ? { error: event.error } : {}),
  })
  return graph
}
```

**为什么 A 而不 是 B —— 这不是风格偏好，是契约逻辑链的要求。**

§11.2「不用 immer」的论证是：**写入点封闭（五个操作点）+ 写入为替换式 ⟹ prev 可安全只存引用 ⟹ 零拷贝逆操作，比通用代理更轻**。

路线 B（journal 记录时 `prev: {...span}`）会同时破坏这条链的两端：

1. **性能论证作废** —— 每次写入都要浅拷贝一个 span 对象。10k span 就是 10k 次对象分配。它把「零拷贝逆操作」直接降级为「每次写入一次浅拷贝」，而这正是 §11.2 排除 immer 时本就想避免的成本。

2. **更危险的是它掩盖问题而非解决问题** —— B 落地后，核心层**再新增任何 mutate 路径都会被 journal 的浅拷贝"恰好兜住"**。于是缺陷隐形，直到某天有人写了深层 mutate（如 `span.outputEntityIds.push(...)`），浅拷贝兜不住，此时 `prev` 与图内对象**共享同一个数组**，回滚静默错误——而那时已无人记得这个隐患。

A 把不变量放回它该在的位置。两者的可维护性差异是决定性的：

- **A 的不变量可以在 review 中检查**：看 `applyEvent` 里有没有 `x.y = z` 形式的赋值。
- **B 的"拷贝得够不够深"无法 review**：它是隐式契约，没人会在 review 时逐字段追一次对象展开的深浅。

**A 是修不变量，B 是打补丁。**

（执行者自己的倾向也是 A，理由表述为「B 把契约的写入语义约束偷换成记录时拷贝技巧」——判断正确。）

**附带核验：A 的"影响面为零"我独立验证成立**：

| 风险点 | 核查结果 |
|---|---|
| `NodeInspector.tsx:154` useMemo 是否缓存旧 span | 依赖数组 `[graph, selectedSpanId, version]`，挂了 version ✅ |
| `scene.ts` buildNodeVisuals 是否持有 span 引用 | 只取 id/name/kind/status 标量，每次 buildScene 重建 ✅ |
| `simulated.ts:27` 归档 | `archive.spans.push({ ...event.span })` 已拷贝 ✅ |
| span.end 后 UI 是否刷新 | `traceStore.ts:117-120` 每事件 `buildScene(..., version+1)` ✅ |

唯一可观察差异是 span 的对象身份，而全仓库无人依赖它。

### 裁决 8-附：加 `Object.freeze` 守卫（硬要求）

A 修复了当前这个 mutate 点，但**不变量本身仍需自动化守卫**——否则下次有人写 `span.xxx = yyy`，又要等 T 卡审查时靠人眼发现。

在 `src/core/graph/build.test.ts` 增加：

```ts
it('写入语义不变量：applyEvent 替换对象而非 mutate（冻结守卫）', () => {
  const graph = createGraph('run-1' as RunId)
  applyEvent(graph, startEvent)      // span 入图
  Object.freeze(graph.spans.get(spanId))   // 冻结图内对象
  expect(() => applyEvent(graph, endEvent)).not.toThrow()   // 严格模式下 mutate 会抛 TypeError
})
```

ES module 默认严格模式，对 frozen object 赋值抛 `TypeError`——**这个测试把"写入是替换式"从"review 时的口头约定"变成 CI 可自动检测的性质**。若将来有人改回 mutate，测试立刻红，且报错信息直指根因。

同类守卫应对 span（span.end）、entity（若未来加 entity.update）各加一条。

### 裁决 9：`run.snapshot` 不记逆操作，且它是**回溯下界**

**采纳执行者的建议，但要把边界条件写死为契约**（他建议的表述「回溯到 0 = 从头重放」不够严谨，见下）。

契约裁决，**写入 `docs/02` §11**：

> **`run.snapshot` 不产生逆操作。它是回溯下界：UI 时间轴可拖范围的下界是「最近一个 snapshot 的应用点」，而非事件流 index 0。**

为什么下界是 snapshot 而不是 index 0：

- **回放场景**：snapshot 在 index 0，两者重合，无差别。
- **断线重连场景**（Phase 2 接真实 SSE 才有）：snapshot 出现在流中间，且会 **clear 五个容器**——它之前的本地历史已被服务端权威全量状态**取代**。重连前的本地数据本就可能不完整（断线期间丢了事件），回溯到它没有意义。
- 因此「最近一个 snapshot 的应用点」才是正确的下界语义。按 index 0 定义会在 Phase 2 静默丢失内容。

当前阶段模拟事件源不产生中间 snapshot，此约束无立即影响——但契约现在写清楚，成本为零；等 Phase 2 再补就是返工。

**关于 `runId` 的两个澄清点**（写入契约）：

1. `graph.runId = event.runId` 的**逆操作不需要**——回溯不越过 snapshot，故同一图实例生命周期内 `runId` 恒定。四类 InverseOp 无需「runId.set」变体。
2. **但静默覆盖必须改为显式拒绝**：若 snapshot 携带的 `runId` 与图实例既有值不同，这属于**事件源错误**（一个 `CausalGraph` 只对应一个 run），应 `throw` 而非静默赋值。这与本项目一贯原则一致——剧本校验就是「非法输入直接抛错，不静默吞掉」。

   风险提示：若此改动导致既有测试失败，说明有测试在跨 run 复用图实例，那本身就是缺陷，**提 BLOCKER，不要改成静默接受**。

## 4. 设计层面的发现

### 4.1 本轮最值得记录的：BLOCKER 机制第一次真正生效

前八张卡里，BLOCKER 机制只是写在文档里的条款。本轮它**真实拦下了一次返工**——而且是代价最高的一类：不是"功能做错"，是"整个模块建立在错误前提上"。

这验证了当初把「遇阻提 BLOCKER、不得自行降级实现」写进红线是对的。**执行者最危险的行为不是做错，而是遇到契约冲突时自作主张选一条路走下去。**

### 4.2 一个观察：写入语义不变量此前一直是隐式的

`build.ts` 文件头注释写了三条硬约束（唯一写入口 / 乱序容错 / O(Δ)），都是 T3 立的。**但没有一条是关于"替换 vs mutate"的**——因为 T3 时不需要：增量建图只关心"图最终对不对"，替换和 mutate 对最终结果完全等价。

是时间旅行这个需求**第一次让对象身份变得有意义**。这类"某个属性此前无关紧要、新需求使其突然成为硬约束"的情况，是契约变更中最容易漏的一类——它不会报错，只会在新功能上静默出错。

裁决 8-附的 `Object.freeze` 守卫正是为此类问题设立的通用手段：**把隐式不变量转成可执行断言**。

### 4.3 对 §11.2 论证的一次压力测试

§11.2 论证「不用 immer」时，我的依据是"写入点封闭"。本轮证明这个依据**比预想的更脆弱**——写入点确实只有五个，但其中一个（span.end）的写入**语义**并不符合要求，而我在设计契约时**默认了它是替换式**，没有验证。

教训：契约里的"前提假设"必须标为**待验证项**，而不是想当然地写进硬约束。本次卡面写了「开工前先确认 applyEvent 是替换还是 mutate」——这个动作救了场，**它应当成为后续所有含前提假设的硬约束的标准配套动作**。
