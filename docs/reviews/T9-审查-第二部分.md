## 3. 🔴 阻塞 B3：`seekTo` 回退路径的 journal 索引错位（严重静默错误）

### 3.1 现象

`checkpoint.ts:170-173`：

```ts
for (let i = session.applied - 1; i >= target; i--) {
  invert(session.graph, session.journal.ops[i] ?? [])   // ← i 是全局事件索引
  session.journal.ops.pop()
}
```

`session.journal.ops` 在 `rebuildFromCheckpoint` 之后是**相对索引**——`ops[k]` 对应 `events[journalBase + k]`，长度 = `applied - journalBase`。而循环变量 `i` 是**全局事件索引**。

当 `journalBase > 0` 时，`ops[i]` 全部越界 → `?? []` → `invert` 对空数组执行 → **图完全不回退**，但 `applied` 照常更新为 `target`。

### 3.2 取证（我实测，探针已删除）

```
events=2157  journalBase=1800  applied=1950  ops.len=150
执行 seekTo(1900) 后：spans=704，期望 spans=685   → 图根本没被回退
```

`ops.length = 1950 - 1800 = 150`，而循环访问 `ops[1949] … ops[1900]` —— 全部越界。

### 3.3 触发条件

1. 一次 `rebuildFromCheckpoint` 且 `journalBase < applied`（即 `target` **不是** `CHECKPOINT_INTERVAL=200` 的倍数）
2. 随后小步回退到 `[journalBase, applied)` 区间内

**这在 UI 上是核心交互**：用户拖到 1950，再往回拖到 1900 —— 完全正常的操作。

### 3.4 界面表现（为什么它特别危险）

时间轴显示"当前 step 1900"，但图里仍是 1950 的内容。**不报错、不崩溃、无任何提示**，用户只会觉得"数据好像不太对"。

### 3.5 为什么 14 个测试没抓到

现有测试的目标点**恰好全部绕开**触发区间：

| 测试 | 路径 | 为何绕开 |
|---|---|---|
| 任意 step 回退（1/200/777/1234/末） | journalBase=0 | 全局索引 == 相对索引，正确 |
| 小步前进 → 950 | 前进 | 不涉回退 |
| 大步前进 → **2000** | 200 的倍数 | `cp.eventIndex = 2000` ⟹ `journalBase = applied = 2000`，此后**任何**回退都满足 `target < journalBase`，走重建路径 |
| 回退越过 journalBase → 50 | 重建 | 不走 invert |
| 往返风暴（9 跳） | 每跳都落在重建或 journalBase=0 | 同上 |

**关键**：第 159 行若把 `seekTo(session, 2000)` 改成 `seekTo(session, 1950)`，测试立刻红。选 200 的倍数不是错误，但**只测边界值恰好漏掉了区间内部**。

### 3.6 修复

```ts
for (let i = session.applied - 1; i >= target; i--) {
  invert(session.graph, session.journal.ops[i - session.journalBase] ?? [])
  session.journal.ops.pop()
}
```

或用相对索引写循环（更清晰，二选一即可）。

**同时修正 `ReplaySession` 的不变量注释（第 76 行）** —— 现写：

```
 * - journal.ops.length === applied；ops[i] 对应 events[i]（i ≥ journalBase）
```

实际应为：

```
 * - journal.ops.length === applied - journalBase；ops[k] 对应 events[journalBase + k]
```

注释与实现不符是这次 bug 的温床——注释写"全局索引"，实现是"相对索引"，两者在 `journalBase = 0` 时无法区分。

### 3.7 必须补的守卫测试

```ts
it('大步前进到非 checkpoint 边界后小步回退（journalBase < applied 区间的 invert 路径）', () => {
  const session = createReplaySession(events)
  seekTo(session, 100)
  seekTo(session, 1950)              // 非 200 倍数 ⟹ journalBase=1800 < applied=1950
  expect(session.journalBase).toBeLessThan(session.applied)   // 前提断言
  seekTo(session, 1900)              // 落在 [journalBase, applied) 内 ⟹ invert 路径
  expect(snapshot(session.graph)).toEqual(snapshot(replayFromScratch(events, 1900)))
})
```

**前提断言 `expect(journalBase).toBeLessThan(applied)` 不可省** —— 否则测试可能因路径改变而"静默失去意义"（这正是现有测试的问题）。

## 4. 设计层面的发现

### 4.1 `?? []` 把编程错误降级成了静默无操作

`invert(session.graph, session.journal.ops[i] ?? [])` —— 若没有 `?? []`，`ops[i]` 为 undefined 时 `invert` 内 `ops.length` 会抛 TypeError，bug 当场暴露。加上它之后，越界被静默吞掉。

**这已是本项目第三次出现同类形态**：

| 轮次 | 位置 | 形态 |
|---|---|---|
| T3 | `consumersIndex` 未命中时返回空列表 | 补边静默丢失 |
| T9 一 | `journal.ts:53` 数组无洞的 `?? []` | 防御守卫 |
| T9 二 | `ops[i] ?? []` | **索引错位被静默吞掉** |

**原则**：当某次访问越界属于**编程错误**而非运行时可变状态时，应让它崩溃或加断言，而不是静默降级。防御性写法适用于"外部输入可能不合法"，不适用于"内部不变量被破坏"。

建议：对"数组无洞"这类防御，在注释里写明前提，或改用 `at()` + 显式检查。

### 4.2 注释与实现不符是 bug 的温床

`ReplaySession` 的不变量注释声称 `ops` 用全局索引，实现是相对索引。两者在 `journalBase = 0`（唯一被测试覆盖的状态）下行为一致，所以**注释错了也测不出来**。

**检查法**：对每条不变量注释，问「**它在什么条件下会与实现分叉？那个条件被测试覆盖了吗？**」——`journalBase = 0` 就是那个未被覆盖的分叉点。

### 4.3 只测边界值会漏掉区间内部

现有测试的目标点全是 200 的倍数（100/2000）或 journalBase=0 的情形，**区间内部从未被覆盖**。这是测试设计的经典盲区：边界值测试很自然地只挑边界。

**检查法**：对每个"区间"，除了边界点，**至少取一个区间内部的点**。
