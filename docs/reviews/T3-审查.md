## 三、实现质量

**做对的地方**：

1. **环检测用 `onPath` + `visited` 两个集合分工** —— 这是本卡最容易写错的地方。只用一个 `visited` 会把菱形汇合（A→B→D、A→C→D）误判成环。执行者不但分对了，还专门写了菱形结构的反例测试。
2. **`edges` 无重复入列** —— 每条边只在「其目标节点首次被访问时」入列，`visited` 保证目标节点只访问一次，因此菱形结构下不会重复。这点没有靠事后 `Set` 去重掩盖，是靠结构保证的。
3. **`run.snapshot` 与增量路径共用同一套 `ingest`** —— 边推导规则只有一份，不会出现"回放时和图生长时规则不一致"的经典分裂。
4. **测试构造图的方式**（直接 `loadScenario` + `resolveEvent` 逐 step 换算，另设一条端到端走 `SimulatedSource` + fake timers）—— 确定性路径保证断言稳定，端到端路径保证两层没接错，两条都断言同一份图结构。这个组合比只写端到端稳得多。

## 四、裁决

### 裁决 2 —— `@vitest/coverage-v8`：**登记，允许安装**

我自己在 T3 卡里写了"覆盖率 ≥80%"却没把工具登记进白名单，这是我的疏漏，不是执行者的问题。

**登记，附带四条约束**：

1. 版本必须与 vitest 主版本对齐：当前 vitest `2.1.9` → 装 `^2.1.9`。版本不一致会报 provider 不匹配。
2. 只能是 `devDependencies`，**且 `src/` 下不得 import 它**（它只在命令行侧运行）。
3. 一并加 `npm run coverage` 脚本，并在 vitest 配置里设：`provider: 'v8'`、`reporter: ['text', 'html']`、`include: ['src/core/**']`、`exclude: ['**/*.test.ts']`。
4. `html` reporter 产物目录加进 `.gitignore`。

**同时修正验收标准本身**（这条比装包更重要）：

- 覆盖率**只考核 `src/core/**`**，`src/render/` 与 `src/ui/` 不纳入（前者靠压测，后者靠目视）
- 提交时要给**完整的 text reporter 输出**（含每个文件的 lines / branches / functions 与未覆盖行号），不是只报一个总数。**理由：一个总数最容易骗人，一张表能直接看出哪一行没测到。**
- 若某文件达不到 80%，**禁止靠删断言、加无意义测试、加 `istanbul ignore` 凑数**。如实报数字与未覆盖行，我来判是补测还是豁免（纯类型模块可以豁免）。

### 裁决 3 —— aging = 半阈值：**采纳，但必须固化**

**采纳比例制，不用绝对时长。** 取舍说明：

- `aging` 的语义是"距离过期还有多少余量"，天然应该相对阈值来量。绝对时长（如固定 1 天）在阈值 7 天和阈值 90 天两种配置下会表现不一致——前者的 aging 区间占 14%，后者只占 1%，同一个"预警"标签在两种配置下分量完全不同。
- 比例制的代价：阈值调大时 aging 区间同比变大。**这不是 bug 而是特性** —— 它让 fresh / aging / stale 三档在任何阈值下都保持一致的相对含义，UI 上的配色语义才不会随配置漂移。
- 半阈值（0.5）意味着预警区间和正常区间对半分。不选 0.8 是因为预警给得太晚，剩 20% 余量时才提示，来不及干预。

**固化要求**：

- 把 `0.5` 提为具名导出常量 `AGING_RATIO`，**UI 要复用它**渲染「aging 区间 3.5–7 天」这类文案，不许在组件里另写一遍 `thresholdMs / 2`
- 判定式已写进 `02` §3，与 `Freshness` 类型放在一起
- Phase 1 做「阈值滑块」时，三档会随滑块实时重算 —— 这正是阈值是查询参数这个设计的兑现点

### 必修项 B1：过期数据影响决策的漏判

`traverse` 的 `entityIds` **只从因果边的 `viaEntityId` 收集**。而 `producedBy === null` 的实体（用户输入、外部系统下发的规则）按契约**不产生因果边**，于是：

> 一份 91 天前的外部文档被决策 span 直接消费 → 它不在 `upstream.entityIds` 里 → 这个决策**不会被标记**。

当前剧本靠 `e-policy` 恰好新鲜而躲过了这个洞 —— **这是运气，不是正确**。`findStaleInfluencedDecisions` 是 Phase 1 的头号卖点 API，漏判恰好发生在"用户直接喂了一份过期材料"这个最典型的场景上。

**修法要求**：遍历时把**每个被访问 span 自身的 `inputEntityIds`** 并入 `entityIds`，而不只是收集边上的 `via`。

语义随之为「链上被消费的全部数据实体」，而非「链上边经由的实体」—— **这才是正确语义**，已同步写进 `02` §6 的注释，不要只改代码不改文档。

**⚠️ 改这条会打破两处既有断言，必须一并更新并在提交材料中说明变更理由**：

1. `query.test.ts:88` `expect(result.entityIds.has('e-policy')).toBe(false)` → 改为 `true`。`e-policy` 是 `s-decide` 的直接输入，本来就该在溯源结果里。
2. `query.test.ts:118-120` `traceDownstream(graph, 's-decide')` 的 `entityIds.size` 从 `0` 变为 `2`（`e-score` + `e-policy`，即 `s-decide` 自身的两个输入）。

其余断言（`query.test.ts:99-101`、`build.test.ts` 全部）不受影响。另需**补一个测试**：决策 span 直接消费一个 91 天前的 `producedBy: null` 实体，必须被 `findStaleInfluencedDecisions` 返回。

### 必修项 B2：`consumersIndex` 降级路径是静默错误

索引内容是「实体 id → 已引用它的 span 列表」，**完全可以从 `graph.spans` 推导**（每个 span 的 `inputEntityIds` 就是这份关系）。但实现做成了挂在图对象身份上的模块级 `WeakMap`，缓存未命中时返回空列表 → **静默不补边**。

两个后果：

1. `createGraph()` 之外构造的图（对象字面量、`as CausalGraph`、JSON 反序列化）拿不到索引。**现在全仓库都走 `createGraph`，所以没人踩到——但它是一个已经上膛、等着被踩的坑。**
2. Phase 1 的 `ReplaySource` 要从 trace 文件反序列化图，**必然踩中这条降级路径**，届时现象是"回放的图少了几条边"，且没有任何报错。

这类 bug 的恶劣程度和 T1 审查发现的三处存储不同步是同一档：**不报错，只是结果悄悄错了**。

**修法要求**：把降级分支从「返回空列表」改为「**扫描 `graph.spans` 重建索引后返回**」。这样索引从"隐藏状态"退化为"纯缓存"，无论图从哪来都正确，且不影响现有增量路径的性能（缓存命中时不重建）。

附带在 `02` §5 补一句：`createGraph()` 是唯一构造入口，禁止对象字面量或反序列化结果直接当 `CausalGraph` 使用。
