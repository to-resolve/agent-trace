## 二、五项修补逐条核验

### 修补 1 · `LayoutEdge` 端点标识 ✅

- `types.ts` 字段顺序与 `02` §10 **逐字一致**（`fromSpanId` / `toSpanId` / `from` / `to` / `viaEntityId` / `state`）
- `buildEdges` 与几何 from/to 同源于 `CausalEdge`，探针证实「graph 有而 layout 缺的边 = 无」
- store 两处消费方（`applyEdgeStates` / `buildBadges`）与 `BadgeAnchor` edge 变体全部改标识定位，**下标推算清零**（`src/` 全文无 `edgeIndex`）
- `applyEdgeStates` 删掉 `graph` 参数：不是顺手重构，是耦合消灭后签名收缩的自然结果，认可

**决策认可**：用 `(fromSpanId, toSpanId, viaEntityId)` 三元组而非二元组作为边标识——`build.ts` 的 `addEdge` 以三元组判重，同一对 span 间可经不同实体存在多条因果边，二元组会碰撞。判断正确。

**超出卡面的加分项**：`hit-test.test.ts` 新增「layout.edges 顺序与徽章顺序故意相反、徽章仍按标识命中」的回归测试。这一条把「下标耦合已消灭」从口头承诺变成了有测试守护的事实——未来有人把 `badgeCenter` 改回按序取值，测试会红。这类"为不变量配守卫"的意识应当在后续保持。

## 四、设计层面的发现

**不改 `01` / `02`：** 本卡是契约的**落实**方而非挑战方，`types.ts` 与 `02` §10 零偏差，没有暴露出契约本身的问题。

**一条值得写进项目记忆的判断**：T4 裁决 5 与 T5 必修 1 指向的是同一个病根——**跨文件的隐式顺序约定**。两次审查、两个不同位置（布局↔store、边数组↔徽章数组）都栽在同一类问题上，说明这不是偶然失误，而是「几何数组 + 平行数组索引」这种数据结构自带的诱惑。T6 的做法（给边加身份标识、配一条乱序回归测试）是这个病根的通用解药。后续凡是出现「A 数组与 B 数组按下标对应」的写法，一律按此处理：加标识，配乱序测试。

**T7 的隐性依赖**：压测卡面上列的三个指标（`layoutGraph` / `updateLayout` / `traceUpstream`）都在 `core/`，而 T6 引入的新成本在 `render/`（徽章锚点查找）与 `store/`（buildScene 组装）。只对 core 测速，会漏掉 T6 自己带来的这笔账。这是本次审查对 T7 最重要的输入。
