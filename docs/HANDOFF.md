## 5. 工作方法（历轮沉淀，不要丢）

### 5.1 审查的核心价值是找「不报错的错」

**测试全绿、类型全过，但结果在特定输入下悄悄错** —— 历轮 8 项必修全属此类。找法：

- 对每个数据结构问「**它从哪来、会不会有第二种来源**」（如反序列化 → 触发 `consumersIndex` 未命中缺陷）
- 对每个集合问「**有没有东西进不来**」（如 `producedBy === null` 的实体 → 决策漏判）
- 对每处跨文件约定问「**有类型保护吗**」（如 `graph.edges` 与 `layout.edges` 下标对齐 → 加端点标识）
- 对每个写入点问「**是替换还是 mutate，prev 引用会不会被污染**」（→ T9 裁决 8）
- 对每个状态判断问「**在回调内调用会怎样**」（→ `pause()` 在 `onEvent` 内被静默忽略）
- 对每个「纯缓存 / 纯派生」结构问「**它什么时候失效**」，而不只是「它能不能重建」（→ T9 B1：可推导 ≠ 会重建，惰性只在缓存不存在时触发，原图一直持有就永远不重建）
- 对每个状态机制问「**被反复来回触发时会怎样**」，而不只是「单次触发对不对」（→ T9 B1：压力测试只做单向回滚，恰好绕开了往返累积）
- 对测试辅助函数问「**它捕获的是引用还是副本**」（→ T9 决策点 4：`snapshot()` 首版捕获 `edges` 引用，基准图生长污染了先拍的快照）
- 对每处 `?? []` / 空值兜底问「**这是在防外部输入，还是在掩盖内部不变量被破坏**」（→ T9 B3：`ops[i] ?? []` 把索引错位降级成静默无操作。**本项目已三次出现同类形态**：T3 `consumersIndex` 返回空列表 / T9 一 `journal.ts:53` / T9 二 `ops[i]`）
- 对每条不变量注释问「**它在什么条件下会与实现分叉？那个条件被测试覆盖了吗**」（→ T9 B3：注释写 `ops[i]` 对应 `events[i]`，实现是相对索引，两者在 `journalBase=0` 时无法区分，而那正是唯一被覆盖的状态）
- 对每个「区间」问「**除了边界点，区间内部被覆盖了吗**」（→ T9 B3：测试目标点全是 200 的倍数，恰好漏掉区间内部）

### 5.2 独立复现，不只读材料

T7 轮我复现出 `p95 = 2.455ms` 而材料声称 `1.567ms`，一度判定不达标；追下去发现是跨 V8 大版本差异，进而催生裁决 6（压测方法学）。**若当时只信材料，这个发现就没了。**

### 5.3 契约含「前提假设」时，必须配套验证动作

T9 的 §11.8 条 6 假设「applyEvent 是替换式写入」，我设计契约时**默认它成立、没验证**。执行者按卡面要求先审计，发现 `span.end` 是 mutate，立即停手提 BLOCKER——**避免整个 `timeline/` 模块建立在错误前提上**。

**制度化**：凡硬约束含前提假设，任务卡必须写明开工前的验证动作 + 验证失败的处理方式（提 BLOCKER）。

### 5.4 把隐式不变量转成可执行断言

口头约定和 review 检查都靠不住。能写成测试就写成测试——T9 的 `Object.freeze` 守卫把「写入是替换式」变成 CI 可检测的性质。

### 5.5 性能数字：环境相关，对外讲浏览器实测

Node 压测数字跨 V8 大版本差 ~50%，**只用于开发期回归，不写进简历**。简历讲浏览器实测（10k 节点 120 帧平移缩放，帧间隔 p50 6.9ms / p95 7.0ms / ≈137fps）——与 Node 版本无关，是用户可感知的真实指标。
