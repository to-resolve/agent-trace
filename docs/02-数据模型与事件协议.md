# 02 · 数据模型与事件协议

> 本文件是项目的**技术核心契约**。`src/core/types.ts` 必须与此文件完全一致。
> 任何修改需先改本文档，再改代码。

## 1. 设计原点：为什么现有工具答不出"为什么"

因为它们只记录一种时间：**事件时间**（数据被读取的时刻）。

而"数据过期"这类根因，需要**两种时间的差值**：

```
数据自身的产生时刻（业务时间）  vs  被本次运行读取的时刻（事件时间）
```

**本项目数据模型的核心差异化就是显式分离这两个时间。** 下面 `DataEntity.createdAt` 与 `DataEntity.observedAt` 是整个项目成立的前提，不允许简化掉任何一个。

## 2. 两套关系：执行树 vs 因果图

本项目同时维护**两套图**，这是理解全局的关键：

| | 执行树 Execution Tree | 因果图 Causal Graph |
|---|---|---|
| 回答 | 谁调用了谁 | 谁的数据影响了谁 |
| 依据 | `span.parentId` | `span.inputEntityIds` 经数据实体中转 |
| 边 | 父子边 | 因果边（带 `viaEntityId`） |
| 形态 | 树（或森林） | **有向图，可能含环** |
| 对应现有工具 | LangSmith 的 span 嵌套 | **本项目独有** |

> 执行树是 LangSmith 已经有的东西，我们保留它用于展示 Agent 层级；
> 因果图才是本项目的价值所在。

## 3. 类型定义

以下内容构成 `src/core/types.ts` 的主体，可直接落地。

```ts
// ---------- 标识 ----------
export type RunId = string
export type SpanId = string
export type EntityId = string
export type AgentId = string

// ---------- 时间：业务时间 vs 事件时间 ----------
/**
 * 一次「观测」记录两个时间：
 * - createdAt：这份数据**本身**是什么时候产生的（业务时间）
 * - observedAt：本次运行**读取**它的时刻（事件时间）
 * 两者之差即数据新鲜度，是本项目检测「过期上下文」类根因的基础。
 */
export interface ObservedAt {
  createdAt: number
  observedAt: number
}

// ---------- 数据实体：因果图的节点之一 ----------
export type EntityKind =
  | 'user_input'    // 用户输入
  | 'context'       // 检索/召回的上下文
  | 'tool_result'   // 工具返回值
  | 'llm_output'    // 模型输出
  | 'decision'      // 决策结论

export interface DataEntity {
  id: EntityId
  kind: EntityKind
  label: string
  /** 产出该实体的 span；null 表示外部输入（用户提问、种子数据） */
  producedBy: SpanId | null
  payload: unknown
  time: ObservedAt
  source: string
  /** 0–1，供置信度传播（Phase 1 的 belief 积分用） */
  trustScore?: number
}

// ---------- 新鲜度：由 time 推导，不存储 ----------
export type FreshnessStatus = 'fresh' | 'aging' | 'stale'

export interface Freshness {
  ageMs: number          // observedAt - createdAt
  status: FreshnessStatus
  /**
   * 仅用于「回记录」本次判定所用的阈值，供 UI 显示「91 天 / 阈值 7 天」。
   * 阈值是**查询参数**（见 findStaleEntities 的入参），不是数据本身的属性。
   * 同一次运行可以用不同阈值查询多次，得到不同的 Freshness 判定结果。
   */
  thresholdMs: number
}

/**
 * aging 档的判定比例：ageMs ≥ thresholdMs * AGING_RATIO 即进入预警区。
 *
 * 为什么用比例而不是绝对时长：aging 的语义是「距离过期还剩多少余量」，
 * 天然应当相对阈值来量。绝对时长（如固定 1 天）在阈值 7 天与 90 天两种
 * 配置下占比相差一个量级，同一个「预警」标签的分量会随配置漂移。
 * 代价是阈值调大时预警区间同比变大——这是特性，不是缺陷。
 *
 * UI 必须复用此常量渲染「aging 区间 3.5–7 天」，禁止在组件里另写 thresholdMs / 2。
 */
export const AGING_RATIO = 0.5

/** 三档判定式（唯一权威定义，query.ts 的 computeFreshness 必须与之一致） */
// ageMs >= thresholdMs                      → 'stale'
// thresholdMs * AGING_RATIO <= ageMs < 阈值  → 'aging'
// ageMs < thresholdMs * AGING_RATIO          → 'fresh'

// ---------- Span：执行树的节点 ----------
export type SpanKind = 'agent' | 'llm' | 'tool' | 'retrieval' | 'decision'
export type SpanStatus = 'running' | 'ok' | 'error'

export interface Span {
  id: SpanId
  runId: RunId
  /** 执行树：调用者 span。顶层为 null */
  parentId: SpanId | null
  agentId: AgentId
  kind: SpanKind
  name: string
  status: SpanStatus
  startedAt: number
  endedAt: number | null
  /** 本 span 消费了哪些数据实体 —— 因果图的入边依据 */
  inputEntityIds: EntityId[]
  /** 本 span 产出了哪些数据实体 —— 因果图的出边依据 */
  outputEntityIds: EntityId[]
  attributes: Record<string, unknown>
  error?: string
}
```

## 4. 因果边的推导规则（本项目核心算法）

**一句话**：如果 span B 消费了实体 E，而 E 由 span A 产出，则存在一条因果边 `A --(E)--> B`。

```ts
export interface CausalEdge {
  fromSpanId: SpanId     // 数据生产者
  toSpanId: SpanId       // 数据消费者
  viaEntityId: EntityId  // 经由哪份数据连接
}
```

推导伪码（增量版本见任务卡 T3）：

```
for each span S:
  for each E in S.inputEntityIds:
    P = entities[E].producedBy
    if P != null and P != S.id:
      edges.add({ from: P, to: S, via: E })
```

**注意点与红线**：
- `producedBy === null` 的实体（用户输入）不产生边，但应作为图的**根节点**渲染，否则溯源链会断在半路
- 自环（`P === S.id`）必须跳过
- **因果图可能有环**（子 Agent 结果回灌、迭代式推理）。所有遍历必须带 visited 集合，禁止无限递归

## 5. 图容器

```ts
export interface CausalGraph {
  runId: RunId
  spans: Map<SpanId, Span>
  entities: Map<EntityId, DataEntity>
  edges: CausalEdge[]
  /** 正向索引：我的输出影响了谁 */
  outgoing: Map<SpanId, CausalEdge[]>
  /** 反向索引：我被谁的数据影响 */
  incoming: Map<SpanId, CausalEdge[]>
}
```

两张索引表是性能关键——溯源查询必须是 O(邻接边) 而非 O(全图)。

> **构造入口**：`createGraph(runId)`（`src/core/graph/build.ts`）是唯一 sanctioned 构造方式。
> **禁止**用对象字面量、`as CausalGraph`、JSON 反序列化结果充当图容器——
> 图对象上挂着实现所需的旁路索引（见 T3 审查必修项 B2），绕过工厂会拿到残缺的图。
> 图内容一律通过 `applyEvent` 增量写入，禁止直接改 `spans` / `entities` / `edges`。

## 6. 查询 API（`src/core/graph/query.ts`）

```ts
export interface TraversalResult {
  spanIds: Set<SpanId>
  /**
   * 子图涉及的**全部**数据实体 = 遍历到的每个 span 自身的 inputEntityIds
   * ∪ 因果边的 viaEntityId。
   *
   * 注意「每个 span 自身的 inputEntityIds」这一项不能省：producedBy === null
   * 的实体（用户输入、外部系统下发的规则）按 §4 不产生因果边，只靠边收集
   * 会把「决策直接消费了一份过期外部材料」这类情况整个漏掉。
   * （见 T3 审查必修项 B1）
   */
  entityIds: Set<EntityId>
  edges: CausalEdge[]
  /** 是否遇到环（用于 UI 提示） */
  hasCycle: boolean
}

/**
 * 由实体的双时间推导新鲜度。判定式见 §3 的 AGING_RATIO 与三档规则。
 * thresholdMs 是查询参数，同一实体用不同阈值调用得到不同结果。
 * UI 用它渲染单个实体的「91 天 / 阈值 7 天」标签。
 */
export function computeFreshness(entity: DataEntity, thresholdMs: number): Freshness

/** 反向溯源：这个 span 的决策，被哪些上游影响（递归到根）。结果含起点 span 自身 */
export function traceUpstream(graph: CausalGraph, spanId: SpanId): TraversalResult

/** 正向传播：这个 span 影响了哪些下游 */
export function traceDownstream(graph: CausalGraph, spanId: SpanId): TraversalResult

/** 找出所有新鲜度不达标的实体 —— 「过期上下文」剧本的判定基础 */
export function findStaleEntities(graph: CausalGraph, thresholdMs: number): DataEntity[]

/** 跨 span 聚合：哪些决策受到了超过阈值天数的过期数据影响（Phase 1 核心卖点） */
export function findStaleInfluencedDecisions(
  graph: CausalGraph,
  thresholdMs: number
): Array<{ span: Span; viaEntities: DataEntity[] }>
```

## 7. 事件协议（自研 AG-UI 子集）

不安装 `@ag-ui/*`。仅实现本项目需要的事件，控制在 300 行内。

```ts
export type AgentEvent =
  | { type: 'run.start';    runId: RunId; startedAt: number; scenarioName?: string }
  | { type: 'run.end';      runId: RunId; endedAt: number; status: 'ok' | 'error' }
  | { type: 'span.start';   runId: RunId; span: Span }
  | { type: 'span.end';     runId: RunId; spanId: SpanId; endedAt: number
                            status: SpanStatus; outputEntityIds: EntityId[]; error?: string }
  | { type: 'entity.create'; runId: RunId; entity: DataEntity }
  /** 全量快照：用于断线重连与离线回放 */
  | { type: 'run.snapshot'; runId: RunId; spans: Span[]; entities: DataEntity[] }
```

**事件顺序约束**：
1. `entity.create` 应当**早于**任何引用它的 `span.start`
2. `span.start` 应当早于同 `spanId` 的 `span.end`
3. `run.snapshot` 只能出现在流的最开始（回放场景）或断线重连后的第一条

> **作用域澄清（重要）**：以上三条是**对事件源的要求**，不是运行时可以假设的前提。
> Phase 2 接真实后端时，乱序、丢事件、断线重连都会违反它们。
> 因此 `src/core/graph/build.ts` **必须对违反保持容错**：引用了尚不存在的实体就跳过
> 不抛错，待该实体到达时补建因果边；`span.end` 早于 `start` 同样静默跳过。
> 容错语义见 T3 硬约束 2，测试覆盖「实体先到 / 实体后到」两条路径。

## 9. 故障剧本格式（`scenarios/*.json`）

剧本是**数据不是代码**——用 JSON 描述一串带延迟的事件，新增剧本不需要改代码。

```ts
export interface ScenarioMeta {
  id: string
  name: string
  description: string
}

/**
 * 剧本中的实体形式：与 DataEntity 同构，但 time 换成相对 run 起点的偏移。
 * 负的 createdAtMs 表示数据产生早于本次运行（即过期数据）。
 */
export interface ScenarioEntity extends Omit<DataEntity, 'time'> {
  timeOffset: {
    /** 数据自身产生时刻相对 run 开始的偏移，负数表示过期数据 */
    createdAtMs: number
    /** 被读取时刻相对 run 开始的偏移；省略时取该事件的计划发生时刻 */
    observedAtMs?: number
  }
}

/**
 * 剧本中的事件：与 AgentEvent 形状相同，但**所有 number 时间字段的语义
 * 都是「相对 run 起点的偏移」**；唯 entity.create 的实体用 timeOffset。
 * run.snapshot 属回放语义，不允许出现在剧本里。
 */
export type ScenarioEvent =
  | Exclude<AgentEvent, { type: 'entity.create' } | { type: 'run.snapshot' }>
  | { type: 'entity.create'; runId: RunId; entity: ScenarioEntity }

export interface Scenario extends ScenarioMeta {
  /** 用于自动化验收：期望用户最终能定位到的根因 span */
  expectedRootCause: { spanId: string; reason: string }
  steps: ReadonlyArray<{
    /** 相对上一个事件的延迟，模拟真实耗时 */
    delayMs: number
    event: ScenarioEvent
  }>
}

/**
 * 剧本事件 → 标准事件：把一切相对偏移换算成绝对时间戳。
 * observedAt 省略时取 planTime（runStartedAt + 累计 delay，在 start() 时预计算），
 * 而非 fire 时的墙上时钟——保证结果只依赖剧本与基准，不受定时器抖动影响。
 */
export function resolveEvent(
  event: ScenarioEvent,
  runStartedAt: number,
  planTime: number,
): AgentEvent
```

> **为什么剧本存相对偏移而不是绝对时间戳**（修订自 T2 审查裁决 1）：
> 剧本要**可重复运行、可跨机器移植、可写进仓库做版本对比**，绝对时间戳三条全做不到。
> 相对偏移不是权宜写法，而是剧本的必要条件。
> `ScenarioEvent` 与 `AgentEvent` 分离，把「存储形式」和「运行时形式」切成两层，
> 中间用 `resolveEvent` 换算——这也是 Phase 2 接真实 SSE 时需要的形状
> （真实流给的是绝对时间，可绕过换算）。

剧本加载后必须校验，非法剧本**直接抛错**，不静默吞掉：剧本是因果推导的输入，坏输入必须尽早暴露。

## 10. 布局结果（`src/core/graph/layout.ts` 输出）

```ts
export interface LayoutNode {
  spanId: SpanId
  layer: number
  x: number; y: number; width: number; height: number
}

export type EdgeVisualState = 'normal' | 'highlighted' | 'dimmed'

export interface LayoutEdge {
  /** 边的端点标识（T4 审查裁决 5）：store 把溯源结果映射到视觉态时
   * 按标识定位，**禁止**依赖「graph.edges 与 layout.edges 下标对齐」
   * 这类跨文件隐式顺序约定——那是静默高亮错边的温床。
   * 渲染层绘制不需要读这两个字段。 */
  fromSpanId: SpanId
  toSpanId: SpanId
  from: { x: number; y: number }
  to: { x: number; y: number }
  viaEntityId: EntityId
  state: EdgeVisualState
}

export interface Layout {
  nodes: Map<SpanId, LayoutNode>
  edges: LayoutEdge[]
  bounds: { width: number; height: number }
  /** 每次变更自增，供渲染层判断是否需要重绘 */
  version: number
}
```

渲染层只读 `Layout`，**不得**直接读取 `CausalGraph`。这保证渲染与数据解耦。
