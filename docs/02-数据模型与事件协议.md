# 02 · 数据模型与事件协议

> 本文件是项目的**技术核心契约**。`src/core/types.ts` 必须与此文件完全一致。
> 任何修改需先改本文档，再改代码。

## 1. 设计原点：为什么现有工具答不出"为什么"

因为它们只记录一种时间：**事件时间**（数据被读取的时刻）。

而"数据过期"这类根因，需要**两种时间的差值**：

```
数据自身的产生时刻（业务时间）  vs  被本次运行读取的时刻（事件时间）
```

**本项目数据模型的核心差异化就是显式分离这两个时间。** 下面 `DataEntity.createdAt` 与 `DataEntity.observedAt` 是整个项目成立的前提，不允许简化掉任何一个。

## 2. 两套关系：执行树 vs 因果图

本项目同时维护**两套图**，这是理解全局的关键：

| | 执行树 Execution Tree | 因果图 Causal Graph |
|---|---|---|
| 回答 | 谁调用了谁 | 谁的数据影响了谁 |
| 依据 | `span.parentId` | `span.inputEntityIds` 经数据实体中转 |
| 边 | 父子边 | 因果边（带 `viaEntityId`） |
| 形态 | 树（或森林） | **有向图，可能含环** |
| 对应现有工具 | LangSmith 的 span 嵌套 | **本项目独有** |

> 执行树是 LangSmith 已经有的东西，我们保留它用于展示 Agent 层级；
> 因果图才是本项目的价值所在。

## 3. 类型定义

以下内容构成 `src/core/types.ts` 的主体，可直接落地。

```ts
// ---------- 标识 ----------
export type RunId = string
export type SpanId = string
export type EntityId = string
export type AgentId = string

// ---------- 时间：业务时间 vs 事件时间 ----------
/**
 * 一次「观测」记录两个时间：
 * - createdAt：这份数据**本身**是什么时候产生的（业务时间）
 * - observedAt：本次运行**读取**它的时刻（事件时间）
 * 两者之差即数据新鲜度，是本项目检测「过期上下文」类根因的基础。
 */
export interface ObservedAt {
  createdAt: number
  observedAt: number
}

// ---------- 数据实体：因果图的节点之一 ----------
export type EntityKind =
  | 'user_input'    // 用户输入
  | 'context'       // 检索/召回的上下文
  | 'tool_result'   // 工具返回值
  | 'llm_output'    // 模型输出
  | 'decision'      // 决策结论

export interface DataEntity {
  id: EntityId
  kind: EntityKind
  label: string
  /** 产出该实体的 span；null 表示外部输入（用户提问、种子数据） */
  producedBy: SpanId | null
  payload: unknown
  time: ObservedAt
  source: string
  /** 0–1，供置信度传播（Phase 1 的 belief 积分用） */
  trustScore?: number
}

// ---------- 新鲜度：由 time 推导，不存储 ----------
export type FreshnessStatus = 'fresh' | 'aging' | 'stale'

export interface Freshness {
  ageMs: number          // observedAt - createdAt
  status: FreshnessStatus
  /**
   * 仅用于「回记录」本次判定所用的阈值，供 UI 显示「91 天 / 阈值 7 天」。
   * 阈值是**查询参数**（见 findStaleEntities 的入参），不是数据本身的属性。
   * 同一次运行可以用不同阈值查询多次，得到不同的 Freshness 判定结果。
   */
  thresholdMs: number
}

/**
 * aging 档的判定比例：ageMs ≥ thresholdMs * AGING_RATIO 即进入预警区。
 *
 * 为什么用比例而不是绝对时长：aging 的语义是「距离过期还剩多少余量」，
 * 天然应当相对阈值来量。绝对时长（如固定 1 天）在阈值 7 天与 90 天两种
 * 配置下占比相差一个量级，同一个「预警」标签的分量会随配置漂移。
 * 代价是阈值调大时预警区间同比变大——这是特性，不是缺陷。
 *
 * UI 必须复用此常量渲染「aging 区间 3.5–7 天」，禁止在组件里另写 thresholdMs / 2。
 */
export const AGING_RATIO = 0.5

/** 三档判定式（唯一权威定义，query.ts 的 computeFreshness 必须与之一致） */
// ageMs >= thresholdMs                      → 'stale'
// thresholdMs * AGING_RATIO <= ageMs < 阈值  → 'aging'
// ageMs < thresholdMs * AGING_RATIO          → 'fresh'

// ---------- Span：执行树的节点 ----------
export type SpanKind = 'agent' | 'llm' | 'tool' | 'retrieval' | 'decision'
export type SpanStatus = 'running' | 'ok' | 'error'

export interface Span {
  id: SpanId
  runId: RunId
  /** 执行树：调用者 span。顶层为 null */
  parentId: SpanId | null
  agentId: AgentId
  kind: SpanKind
  name: string
  status: SpanStatus
  startedAt: number
  endedAt: number | null
  /** 本 span 消费了哪些数据实体 —— 因果图的入边依据 */
  inputEntityIds: EntityId[]
  /** 本 span 产出了哪些数据实体 —— 因果图的出边依据 */
  outputEntityIds: EntityId[]
  attributes: Record<string, unknown>
  error?: string
}
```

## 4. 因果边的推导规则（本项目核心算法）

**一句话**：如果 span B 消费了实体 E，而 E 由 span A 产出，则存在一条因果边 `A --(E)--> B`。

```ts
export interface CausalEdge {
  fromSpanId: SpanId     // 数据生产者
  toSpanId: SpanId       // 数据消费者
  viaEntityId: EntityId  // 经由哪份数据连接
}
```

推导伪码（增量版本见任务卡 T3）：

```
for each span S:
  for each E in S.inputEntityIds:
    P = entities[E].producedBy
    if P != null and P != S.id:
      edges.add({ from: P, to: S, via: E })
```

**注意点与红线**：
- `producedBy === null` 的实体（用户输入）不产生边，但应作为图的**根节点**渲染，否则溯源链会断在半路
- 自环（`P === S.id`）必须跳过
- **因果图可能有环**（子 Agent 结果回灌、迭代式推理）。所有遍历必须带 visited 集合，禁止无限递归

## 5. 图容器

```ts
export interface CausalGraph {
  runId: RunId
  spans: Map<SpanId, Span>
  entities: Map<EntityId, DataEntity>
  edges: CausalEdge[]
  /** 正向索引：我的输出影响了谁 */
  outgoing: Map<SpanId, CausalEdge[]>
  /** 反向索引：我被谁的数据影响 */
  incoming: Map<SpanId, CausalEdge[]>
}
```

两张索引表是性能关键——溯源查询必须是 O(邻接边) 而非 O(全图)。

> **构造入口**：`createGraph(runId)`（`src/core/graph/build.ts`）是唯一 sanctioned 构造方式。
> **禁止**用对象字面量、`as CausalGraph`、JSON 反序列化结果充当图容器——
> 图对象上挂着实现所需的旁路索引（见 T3 审查必修项 B2），绕过工厂会拿到残缺的图。
> 图内容一律通过 `applyEvent` 增量写入，禁止直接改 `spans` / `entities` / `edges`。

```ts
export interface TraversalResult {
  spanIds: Set<SpanId>
  /**
   * 子图涉及的**全部**数据实体 = 遍历到的每个 span 自身的 inputEntityIds
   * ∪ 因果边的 viaEntityId。
   *
   * 注意「每个 span 自身的 inputEntityIds」这一项不能省：producedBy === null
   * 的实体（用户输入、外部系统下发的规则）按 §4 不产生因果边，只靠边收集
   * 会把「决策直接消费了一份过期外部材料」这类情况整个漏掉。
   * （见 T3 审查必修项 B1）
   */
  entityIds: Set<EntityId>
  edges: CausalEdge[]
  /** 是否遇到环（用于 UI 提示） */
  hasCycle: boolean
}

/**
 * 由实体的双时间推导新鲜度。判定式见 §3 的 AGING_RATIO 与三档规则。
 * thresholdMs 是查询参数，同一实体用不同阈值调用得到不同结果。
 * UI 用它渲染单个实体的「91 天 / 阈值 7 天」标签。
 */
export function computeFreshness(entity: DataEntity, thresholdMs: number): Freshness

/** 反向溯源：这个 span 的决策，被哪些上游影响（递归到根）。结果含起点 span 自身 */
export function traceUpstream(graph: CausalGraph, spanId: SpanId): TraversalResult

/** 正向传播：这个 span 影响了哪些下游 */
export function traceDownstream(graph: CausalGraph, spanId: SpanId): TraversalResult

/** 找出所有新鲜度不达标的实体 —— 「过期上下文」剧本的判定基础 */
export function findStaleEntities(graph: CausalGraph, thresholdMs: number): DataEntity[]

/** 跨 span 聚合：哪些决策受到了超过阈值天数的过期数据影响（Phase 1 核心卖点） */
export function findStaleInfluencedDecisions(
  graph: CausalGraph,
  thresholdMs: number

```

## 7. 事件协议（自研 AG-UI 子集）

不安装 `@ag-ui/*`。仅实现本项目需要的事件，控制在 300 行内。

```ts
export type AgentEvent =
  | { type: 'run.start';    runId: RunId; startedAt: number; scenarioName?: string }
  | { type: 'run.end';      runId: RunId; endedAt: number; status: 'ok' | 'error' }
  | { type: 'span.start';   runId: RunId; span: Span }
  | { type: 'span.end';     runId: RunId; spanId: SpanId; endedAt: number
                            status: SpanStatus; outputEntityIds: EntityId[]; error?: string }
  | { type: 'entity.create'; runId: RunId; entity: DataEntity }
  /** 全量快照：用于断线重连与离线回放 */
  | { type: 'run.snapshot'; runId: RunId; spans: Span[]; entities: DataEntity[] }
```

**事件顺序约束**：
1. `entity.create` 应当**早于**任何引用它的 `span.start`
2. `span.start` 应当早于同 `spanId` 的 `span.end`
3. `run.snapshot` 只能出现在流的最开始（回放场景）或断线重连后的第一条

> **作用域澄清（重要）**：以上三条是**对事件源的要求**，不是运行时可以假设的前提。
> Phase 2 接真实后端时，乱序、丢事件、断线重连都会违反它们。
> 因此 `src/core/graph/build.ts` **必须对违反保持容错**：引用了尚不存在的实体就跳过
> 不抛错，待该实体到达时补建因果边；`span.end` 早于 `start` 同样静默跳过。
> 容错语义见 T3 硬约束 2，测试覆盖「实体先到 / 实体后到」两条路径。

## 9. 故障剧本格式（`scenarios/*.json`）

剧本是**数据不是代码**——用 JSON 描述一串带延迟的事件，新增剧本不需要改代码。

```ts
export interface ScenarioMeta {
  id: string
  name: string
  description: string
}

/**
 * 剧本中的实体形式：与 DataEntity 同构，但 time 换成相对 run 起点的偏移。
 * 负的 createdAtMs 表示数据产生早于本次运行（即过期数据）。
 */
export interface ScenarioEntity extends Omit<DataEntity, 'time'> {
  timeOffset: {
    /** 数据自身产生时刻相对 run 开始的偏移，负数表示过期数据 */
    createdAtMs: number
    /** 被读取时刻相对 run 开始的偏移；省略时取该事件的计划发生时刻 */
    observedAtMs?: number
  }
}

/**
 * 剧本中的事件：与 AgentEvent 形状相同，但**所有 number 时间字段的语义
 * 都是「相对 run 起点的偏移」**；唯 entity.create 的实体用 timeOffset。
 * run.snapshot 属回放语义，不允许出现在剧本里。
 */
export type ScenarioEvent =
  | Exclude<AgentEvent, { type: 'entity.create' } | { type: 'run.snapshot' }>
  | { type: 'entity.create'; runId: RunId; entity: ScenarioEntity }

export interface Scenario extends ScenarioMeta {
  /** 用于自动化验收：期望用户最终能定位到的根因 span */
  expectedRootCause: { spanId: string; reason: string }
  steps: ReadonlyArray<{
    /** 相对上一个事件的延迟，模拟真实耗时 */
    delayMs: number
    event: ScenarioEvent
  }>
}

/**
 * 剧本事件 → 标准事件：把一切相对偏移换算成绝对时间戳。
 * observedAt 省略时取 planTime（runStartedAt + 累计 delay，在 start() 时预计算），
 * 而非 fire 时的墙上时钟——保证结果只依赖剧本与基准，不受定时器抖动影响。
 */
export function resolveEvent(
  event: ScenarioEvent,
  runStartedAt: number,
  planTime: number,
): AgentEvent
```

> **为什么剧本存相对偏移而不是绝对时间戳**（修订自 T2 审查裁决 1）：
> 剧本要**可重复运行、可跨机器移植、可写进仓库做版本对比**，绝对时间戳三条全做不到。
> 相对偏移不是权宜写法，而是剧本的必要条件。
> `ScenarioEvent` 与 `AgentEvent` 分离，把「存储形式」和「运行时形式」切成两层，
> 中间用 `resolveEvent` 换算——这也是 Phase 2 接真实 SSE 时需要的形状
> （真实流给的是绝对时间，可绕过换算）。

剧本加载后必须校验，非法剧本**直接抛错**，不静默吞掉：剧本是因果推导的输入，坏输入必须尽早暴露。

## 11. 时间旅行（`src/core/timeline/`）

> 本节为 T9 而立。**设计决策归指挥者，实现细节归执行者。**

### 11.1 设计原点：能回答"如果当时那份数据没过期，决策会是什么"

时间旅行不是"撤销按钮"。它的价值是**反事实归因**：回到某个 step，改掉当时的输入（比如把过期 91 天的简历换成新版本），让执行从这里分叉出新分支，对比两条分支的决策差异。这才是「哪份数据导致了这个决策」的终极证据——不是推理出来的，是**跑出来的**。

配套能力是回溯（拖时间轴回到任意 step 查看当时的图状态）。

### 11.2 为什么不用 immer（硬决策）

**不引入 immer，逆操作自研。** 三个理由，第三条是决定性的：

1. **依赖白名单**（`01` §2）未登记 immer，引入需走裁决。
2. **immer 的 Map 代理在热路径上代价过高**。T9 之前 `updateLayout` 单事件已压到 ~2ms（T8 实测 Node 24 = 1.777ms）。时间旅行若要求每事件走一次 `produce` + `produceWithPatches`，等于给这条路径重新套上代理层，T7 的优化成果会被抵消。
3. **`CausalGraph` 的变更是有限且封闭的操作集**（见 §5：`applyEvent` 是唯一写入口）。对已知操作集记录逆操作，比通用 diff 更简单、更省内存、零依赖——**通用性在这里是负债不是资产**。

> 面试讲法：「我没用 immer，因为这个图结构的写入是封闭的五个操作点，自研逆操作比通用代理更轻，且不引入运行时开销。用 immer 是我第一个排除的方案。」

### 11.3 逆操作（InverseOp）

```ts
/**
 * 把一个 applyEvent 的变更还原回去。
 * 全部是「设置回某个确定值」而非「增量删除」——幂等、可重复应用、不依赖数组当前状态。
 */
export type InverseOp =
  /** spans.set(id, prev)；prev 为 null 表示删除该键 */
  | { kind: 'span.set'; spanId: SpanId; prev: Span | null }
  /** entities.set(id, prev)；prev 为 null 表示删除该键 */
  | { kind: 'entity.set'; entityId: EntityId; prev: DataEntity | null }
  /** graph.edges 截断到 length（新增的边总是 push 在尾部，见 §4） */
  | { kind: 'edges.truncate'; length: number }
  /** 邻接索引截断：outgoing/incoming 的某个 spanId 数组截断到 length */
  | { kind: 'adj.truncate'; table: 'outgoing' | 'incoming'; spanId: SpanId; length: number }
```

**硬约束**：
- 逆操作**必须按 LIFO 逆序应用**（后产生的先还原）
- `prev` 存的是**完整对象引用**，不是增量字段——span 是小对象，存完整值比存字段 diff 简单且不易错
- `adj.truncate` 的 `length` 为 0 时**必须删除该键**（`Map.delete`），不能留空数组——空数组会让后续 `?? []` 分支与真实"无邻接边"产生歧义

### 11.4 Journal

```ts
/** 事件流的逆操作日志。ops[i] = 应用第 i 个事件所产生的逆操作序列（已按产生顺序排列） */
export interface Journal {
  ops: InverseOp[][]
}

export function createJournal(): Journal
/** 按 LIFO 逆序应用一组逆操作，把图还原到应用该事件之前 */
export function invert(graph: CausalGraph, ops: readonly InverseOp[]): void
```

**§5 的 `applyEvent` 增加可选第三参数**：

```ts
export function applyEvent(graph: CausalGraph, event: AgentEvent, journal?: Journal): void
```

- `journal` 为 `undefined` 时**零开销**（既有调用点行为完全不变）
- 传入时，在每个写入点前 `journal.ops[eventIndex].push(inverseOp)`
- **禁止**为了记日志而改变任何既有写入语义

### 11.5 Checkpoint

纯逆操作回放从头开始太慢（T8 实测 10k 完整回放 ~90s），必须做检查点：

```ts
export interface Checkpoint {
  /** 已应用前 eventIndex 个事件之后的图状态 */
  eventIndex: number
  graph: CausalGraph   // 深拷贝，与原图零共享引用
  layout: Layout       // 深拷贝（Layout 是纯数据，见 §10）
}

/** 深拷贝：Map / 数组 / 节点对象逐层复制，禁止结构共享 */
export function cloneGraph(graph: CausalGraph): CausalGraph
export function cloneLayout(layout: Layout): Layout
```

**检查点间隔 `CHECKPOINT_INTERVAL = 200`**（执行者可按实测调整，但必须在提交材料里给出依据）。

回溯算法：
1. 找到 `eventIndex <= target` 的最后一个 checkpoint
2. 从它的 `graph` / `layout` 深拷贝出发
3. **正向重放** `events[checkpoint.eventIndex .. target)`（记录 journal 以便继续）
4. 返回该时刻状态

复杂度：O(CHECKPOINT_INTERVAL + 图克隆) 而非 O(target)。

### 11.6 Branch（分叉）

```ts
export interface Branch {
  id: string
  /** 从主时间线的第几个事件后分叉（baseEventIndex 个事件已应用） */
  baseEventIndex: number
  /** 该分支在分叉点之后的事件序列（含「修改过的历史」与「新执行」） */
  events: AgentEvent[]
  /** 分叉时的人工改动说明（UI 展示用，如「把简历换成 v2」） */
  note: string
}

export interface Timeline {
  mainEvents: AgentEvent[]        // 原始事件流
  branches: Branch[]
  activeBranchId: string | null   // null = 主线
}

export function forkBranch(timeline: Timeline, atEventIndex: number, note: string): Branch

/** 为分支按需建执行会话（裁决 11，2026-09-06 增补）：
 *  组合流 = 主线前缀 + 分支自有事件；复用主线 ≤ baseEventIndex 的
 *  checkpoint 深拷贝，其后增量应用。与 forkBranch 分离让 store 可
 *  先登记分支、UI 切换到哪条才建哪条的图。 */
export function createBranchSession(
  timeline: Timeline,
  branch: Branch,
  mainSession: ReplaySession,
```

**硬约束**：
- `forkBranch` **不得修改主时间线**——从 checkpoint 深拷贝出发，原分支保持原样
- 分支上的图是**独立的 `CausalGraph` 实例**，与主线的图不共享任何可变结构
- 分支的 `runId` 必须派生自主线（如 `${runId}#fork-${n}`），保证 `createGraph` 的唯一构造约束（§5）不被绕过

**裁决 11（2026-09-06，第四部分审查）**：
1. **fork（纯数据登记）与建图（`createBranchSession`）分离**——采纳，契约增补上列签名
2. **分支图 runId 的一次显式赋值合法**（`cloneGraph` 后 `graph.runId = branch.id`）：runId 是图元数据而非因果结构，§5 约束的是结构写入（spans/entities/edges/邻接表）。**边界：元数据赋值仅限构造路径内的 runId 一次性设置，不得扩大解释为构造期可直改结构**
3. **注入事件的 runId 保持主线形态**（组合流前缀一致；`applyEvent` 只对 `run.snapshot` 校验 runId）。⚠️ Phase 2 若真实后端的事件流含 mid-stream `run.snapshot`，组合时需改写其 runId 或在分支语义下另行处理——当前数据源（synth/剧本 JSON）无此形态
4. **分支会话应复用主线 ≤ baseEventIndex 的 checkpoints**（共享引用安全：Checkpoint 只读、使用时 clone）——保证 `ReplaySession` 的 checkpoint 覆盖不变量在分支会话同样成立，避免「拖分支时间轴回退 → 从零重放」的性能悬崖。配套要求：`rebuildFromCheckpoint` 从 checkpoint clone 后须以 `session.runId` 归一图元数据（主线会话为 no-op）

### 11.8 硬约束汇总

1. **核心层零框架依赖**（`01` §4）——`src/core/timeline/` 不得 import react / zustand
2. **零新依赖**——不引 immer、不引任何状态管理库
3. `CausalGraph` 的构造与写入仍以 §5 为唯一权威，**时间旅行不得绕过 `applyEvent` 直接改图**
4. 因果边推导规则以 §4 为唯一权威，**分支上的图必须用同一套规则推导**——否则"对比两条分支"失去意义
5. Checkpoint 与 fork 的图**必须深拷贝**，禁止结构共享（这是"改了 A 分支结果 B 分支也变了"这类幽灵 bug 的唯一来源）
6. 逆操作的 `prev` 引用指向的历史对象**不得被后续事件原地修改**——`applyEvent` 写入 span 时必须替换对象而非 mutate 既有对象（若现有实现是 mutate，执行者须提 BLOCKER）

   > **前提已在 T9 验证并执行（裁决 8）**：原 `span.end` 路径是字段级 mutate（`build.ts:145-148`），违反本条；已裁决改为替换写入。
   > **不得用「journal 记录时浅拷贝 prev」替代本条**（裁决 8 排除的路线 B）：那会把"零拷贝逆操作"降级为"每次写入一次浅拷贝"，且新增 mutate 路径会被浅拷贝恰好掩盖，直到某个深层字段被 mutate 时才暴露，届时 `prev` 与图内共享同一嵌套对象，回滚静默错误。
   > **本条由冻结守卫测试保护**：`build.test.ts` 中 `Object.freeze` 图内对象后 `applyEvent`，严格模式下 mutate 会抛 `TypeError`。改动写入语义时此测试必须保持通过——它把"替换 vs mutate"从 review 时的口头约定变成 CI 可自动检测的性质。

7. **`run.snapshot` 不产生逆操作，且它是回溯下界** —— 时间轴可拖范围的下界是「**最近一个 snapshot 的应用点**」，**而非事件流 index 0**（裁决 9）

   - 回放场景两者重合；断线重连场景（Phase 2）snapshot 出现在流中间且会 clear 五个容器，它之前的本地历史已被服务端权威全量状态**取代**，且重连前的本地数据本就可能不完整（断线期间丢事件），回溯到它没有意义
   - 按 index 0 定义下界，会在 Phase 2 静默丢失内容
   - 推论：`graph.runId = event.runId` 不需要逆操作——回溯不越过 snapshot，同一图实例生命周期内 `runId` 恒定

8. **`runId` 冲突必须显式拒绝** —— 一个 `CausalGraph` 只对应一个 run。`run.snapshot` 携带的 `runId` 与图实例既有值不同属**事件源错误**，应 `throw`，不得静默覆盖（与 §9「非法剧本直接抛错，不静默吞掉」同源原则）。若因此导致既有测试失败，说明有测试在跨 run 复用图实例，那本身就是缺陷——提 BLOCKER，不要改为静默接受

### 11.9 验收口径（T9）

- 回溯到任意 step 后的图状态，与**从头回放该 step** 得到的图状态**逐字段相等**（关键断言）
- fork 出的分支修改后，**原分支状态不变**
- 时间旅行开启后，`updateLayout` 单事件耗时**退化不超过 20%**（保护 T7/T8 的性能成果；若超，改回"仅在需要时挂载 journal"）
- 10k 事件流下，回溯到 step 5000 的耗时 **< 200ms**（checkpoint 生效的证据）
