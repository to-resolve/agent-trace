## 1. 实现记录

### build.ts —— 增量构建

- `applyEvent(graph, event)` 为**唯一写入口**：`edges` / `outgoing` / `incoming` 三处冗余存储只在私有函数 `addEdge` 内原子更新（幂等：同 from/to/via 的边只存在一份），模块内其他函数一律不触碰这三处。`createGraph(runId)` 为必需的图容器工厂。
- **乱序容错（硬约束 2）**：`span.start` 引用尚不存在的实体时跳过不抛错；实体经 `entity.create` 到达时，通过「实体 → 消费 span 列表」的反查索引（模块级 `WeakMap<CausalGraph, Map<EntityId, SpanId[]>>`，不污染 02 契约的图容器）补建因果边。两条路径（实体先到 / 实体后到）都覆盖了自环跳过与 `producedBy === null` 不产边。
- **增量性（硬约束）**：每个事件只处理自己涉及的一个 span / entity；`applyEvent` 返回同一 graph 引用，`spans` Map、`edges` 数组等容器引用稳定（测试断言 `toBe`），证明是原地增量而非重建。
- `run.snapshot` 语义为全量重置：清空后按「先实体后 span」重放，与增量路径共用同一套 `ingest` 函数，边推导规则单份维护。
- `span.end` 合并 `status / endedAt / outputEntityIds / error` 进图内副本；span 未 start 时静默跳过（乱序容错）。span / entity 入图时浅拷贝，保证 `span.end` 更新不污染已发给消费者的事件对象。

### query.ts —— 双向溯源

- `traceUpstream` / `traceDownstream`：走 `incoming` / `outgoing` 索引的 DFS，复杂度 O(邻接边)。环安全靠两个集合分工：`onPath`（当前 DFS 路径，再次到达即回边 → `hasCycle = true`）与 `visited`（已完成分支，菱形汇合不算环）——测试中专门验证了菱形结构 `hasCycle === false`。
- `computeFreshness(entity, thresholdMs)`：02 第 3 节 `Freshness` 类型的判定入口（findStaleEntities 的核心），`thresholdMs` 仅回记录本次判定所用阈值（硬约束 3：阈值是查询参数，同一图不同阈值得到不同判定，测试覆盖三档变化）。
- `findStaleEntities` / `findStaleInfluencedDecisions`（02 第 6 节全部四个 API + `TraversalResult` 类型均已落地）。

## 4. 决策点与偏离说明

1. **`createGraph(runId)` 辅助函数**：任务卡只给了 `applyEvent(graph, event)` 签名，图容器需要初始化入口，新增 `createGraph`（同时初始化 WeakMap 索引）。不在输出清单但为实现必需。
2. **乱序反查索引用模块级 `WeakMap`**：`CausalGraph` 是 02 固定契约（六字段），不能私加字段；索引挂在图实例上、随图回收，且只被 `applyEvent` 家族读写，不违反「唯一写入口」。
3. **新增导出 `computeFreshness(entity, thresholdMs)`**：02 第 3 节定义了 `Freshness` 但第 6 节的查询 API 均不产出它；任务卡验收「同一图用不同阈值查询，Freshness.status 随之变化」需要单实体 × 阈值的判定入口。它是 `findStaleEntities` 的判定核心，`findStaleEntities` 等签名与 02 第 6 节逐字一致。
4. **三档判定式（02 未定义，自行落地）**：`ageMs ≥ thresholdMs` → stale；`thresholdMs/2 ≤ ageMs < thresholdMs` → aging；否则 fresh。「半阈值」为我的拍板——02 只给了三档枚举没给判定式。若架构负责人有更合适的口径（如 aging 用绝对时长而非比例），改一处函数即可。
5. **`TraversalResult` 含起点 span 自身**：`traceUpstream(s-decide)` 的 `spanIds` 含 `s-decide`。02 未明确；含起点让 UI 高亮时「被点击节点 + 影响链」一次取全，我倾向如此。
6. **`run.snapshot` 的重放顺序**：先 entities 后 spans（保证 span 灌入时实体已存在，走「立即建边」路径）。若快照本身有乱序引用，span 先行挂起、实体到达补边的路径同样兜底。
7. **重复 `entity.create`（同 id、producedBy 变化）不删除旧边**：属 `context-override` 剧本（Phase 1）的冲突处理范畴，本卡不实现。
8. **测试构造 stale-context 图的方式**：直接 `loadScenario` + `resolveEvent` 逐 step 换算（确定性，无时钟依赖），另设一个端到端用例走 `SimulatedSource` + fake timers 验证全链路，二者图结构断言一致。
