# 提交材料

**执行者每完成一张任务卡，在此目录提交材料。** 架构负责人从此处读取并审查，审查结论写入 `../reviews/`。

```
docs/submissions/   ← 执行者写（提交材料）
docs/reviews/       ← 架构负责人写（审查结论）
```

## 提交规范

1. 一张任务卡一个文件：`T{n}-提交.md`（如 `T1-提交.md`）
2. 用下方模板，**五个章节缺一不可**
3. 提交后**立即停止**，不要继续做下一张卡
4. 被退回时：**在原文件追加「修订记录」章节**，不要新建 v2 文件，便于对比

## 任务状态流转

```
todo ──实现──> submitted ──审查通过──> done
                   │
                   ├──审查退回──> todo（修订后重新提交，追加修订记录）
                   └──遇阻──────> blocked（等待裁决）
```

- 状态写在 `../03-任务看板.md` 对应任务卡上
- 执行者提交时改为 `submitted`；**改为 `done` 是架构负责人的权限**，不要自己改

## 提交模板

```md
# T{n} 提交

**任务卡**：T{n} · <任务名>
**提交时间**：YYYY-MM-DD
**状态**：submitted

## 1. 实现记录
- 做了什么（简明扼要，不要复述代码）
- 关键实现决策（若有）

## 2. 变更文件清单
### 新增
- `src/core/types.ts` —— 数据模型类型定义
### 修改
- （无则写"无"）

## 3. 自测输出
### `npm run tsc`
```
<粘贴完整终端输出，不要只写"通过">
```
### `npm run dev`
```
<启动结果，能否正常访问>
```
### `npm test`（若本卡涉及测试）
```
<输出，或写"本卡不涉及">
```

## 4. 决策点与偏离说明
- 与 `docs/` 文档的任何偏差及原因
- 自行做的任何决策
- 没有就写"无"（**这一项不许留空**）

## 5. BLOCKER
- 需要架构负责人裁决的问题
- 没有就写"无"

## 修订记录
（仅在被退回后追加，每次修订一条）

### 修订 1 · YYYY-MM-DD
- 修订内容：<针对审查第 N 条问题>
- 涉及文件：<路径>
```

## 硬性要求

- **自测输出必须是真实终端输出**，禁止写"应该能过""无报错"这类描述。没有输出视为未自测，不予审查
- **变更文件清单必须给完整路径**（相对项目根目录），我需要按图索骥去读代码
- **第 4 项不许留空** —— 你自行拍板的任何决策都必须写出来，否则审查时容易漏掉
