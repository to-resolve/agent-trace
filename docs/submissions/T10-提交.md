## 4. 决策点与偏离说明

1. **store.fork 也加了守卫（超出卡面一行）**：卡面只要求 UI 禁用 + title。但 UI 禁用无法被测试覆盖（项目无组件测试框架，引入 @testing-library 违反依赖白名单）——把守卫下沉到 store 层后：①可测 ②防未来绕过 UI 的调用路径。UI 禁用 + store 守卫双保险，测试覆盖后者
2. **两个守卫合在一条测试**：它们共享同一条 store 全链路（跑剧本 → 时间旅行 → 分叉 → 切分支 → 注入），拆成两条只会重复整套 setup。一条测试内依次断言两个守卫的行为
3. **守卫测试走 store 全链路而非 mock**：直接调 `useTraceStore` 的 action（init → startRun → enterTimeline → seek → fork → switchBranch → inject）。发现并修正了一个测试时序问题：fake timers 必须先于 startRun 启用（事件源 setTimeout 要注册进 fake 队列）——这个坑本身是 e2e 测试与 store 集成的知识点
4. **BranchPanel 两种拒绝提示的区分**：守卫返回 false 有两种原因（已注入 / 分叉点不适用）。用 rerunDone 本地态禁用按钮（已注入路径）+ else 提示分叉点不适用——两个失败原因都可感知，无静默
5. **package.json 补 preview script**：卡面要求「npm run preview 下验证」但 script 缺失（Vite 脚手架默认不含）。加的是 npm script 非依赖，不违反白名单
6. **README 数字取舍**：196（而非卡面写的 195——本卡 +1 守卫测试后为 196，与 npm test 输出一致）；137fps 与 25.9ms 分别取自 T7 提交材料（浏览器实测）与 T9 审查第五部分 §4（Node 22 复跑）——任务卡指定来源，逐项可核对。「3 秒定位」「60–90 分钟」出自项目章程背景叙述（AGENTS.md 引用的公开横评结论）
7. **README 未列 shot-4/5**：界面区用 T5 截图（溯源）+ shot-2（决策对比）已覆盖两个核心场景；shot-4/5 与 shot-1/2/3 是同一 UI 的 preview 版本（防重复）。shot-4/5 在本材料与 T10-2 验证记录中使用
8. **架构图用数据流视角**：`source → build → layout → render → store → ui` 的排列是数据流方向；依赖方向（ui → store → core）在下方要点单独写明——两个视角都在，避免混淆
9. **workflow 用 Node 22**：与指挥者审查环境（Node 22.22.2）一致；package.json engines >=22 不冲突
