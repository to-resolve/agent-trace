# 00 · 项目章程

## 1. 要解决的具体问题

一个多 Agent 系统（检索 Agent → 评估 Agent → 决策 Agent）做出了错误决策。开发者要查明原因。

**现有工具（LangSmith / Langfuse / Arize Phoenix / AgentOps / LangGraph Studio）提供的视图**：瀑布时间线。
显示"检索在 10:00:01 取了简历、评估在 10:00:05 打了 60 分、决策在 10:00:08 拒绝"。

**这回答不了的问题**：到底是哪一份数据、通过哪条路径影响了最终决策？

公开横评用同一场景测试了上述五款工具（三 Agent 协作 + 一份过期 14 天的上下文导致坏决策），结论：
- 五款**全部无法直接回答因果性问题**
- LangSmith / Phoenix / Langfuse 需手工展开 JSON、心算时间差，定位根因耗时 60–90 分钟
- LangGraph Studio 单条 trace 体验好，但**无法跨 trace 聚合查询**
- 唯一通过测试的方案是自建图数据库 + 手写 Cypher 查询

**本项目的答案**：点一下"拒绝"节点，反向高亮整条影响链——拒绝 ← 评分 60 ← 简历数据（已过期 91 天），根因节点红色标注。3 秒定位。

## 2. 项目定位

| | 调试普通代码 | 调试 Agent |
|---|---|---|
| 已有 | Chrome DevTools 的 Network 瀑布图 | LangSmith 的 trace 时间线 |
| **本项目** | Memory 面板的引用关系图 / Vue DevTools 的组件依赖图 | **provenance 有向图** |

一句话对外表述：**Agent 的 Vue DevTools —— 别人做瀑布图，我们做依赖关系图。**

## 3. 目标用户

写 Agent 的开发者。这是**面向开发者的调试工具**，不是面向普通用户的聊天产品。
所有交互设计以此为准：信息密度优先、键盘可达、状态可追溯，不追求花哨动效。

## 4. 成功标准（可验收）

**Phase 0 垂直切片（T1–T5）**
- [ ] 浏览器打开即见一张实时构建的因果图（≥20 个 span）
- [ ] 点击任意节点，反向高亮其全部上游影响链，正向高亮全部下游受影响节点
- [ ] "过期上下文"剧本下，点最终决策节点能在 3 次点击内看到标红的过期数据节点
- [ ] 图交互（缩放 / 平移 / 点击）在 20 span 规模下无卡顿

**Phase 1 完整版（T6–T8）**
- [ ] 10000 span 规模下交互保持 60fps
- [ ] 时间旅行：回溯任意步骤、修改状态、fork 新执行分支
- [ ] 支持 trace 文件导入与离线回放
- [ ] 可静态部署，产物可直接打开链接体验（无需起后端）

## 5. 本项目**不是**什么（边界，越界即砍）

- ❌ 不是 Agent 框架。不实现 Agent 编排、不实现 LLM 调用。被观测对象是外部系统。
- ❌ 不是聊天界面。不做对话 UI、不做消息气泡流。
- ❌ 不是 LLM 应用。项目自身不调用任何大模型 API。
- ❌ 不是通用 APM。不关心 CPU、内存、HTTP 状态码这类基础设施指标。
- ❌ 不是 LangChain / LangGraph 的插件。保持框架无关。

## 6. 红线（违反即退回重做）

1. **核心层零框架依赖** —— `src/core/`、`src/render/` 禁止 import React 或任何 UI 框架。纯 TypeScript。
2. **不引第三方图布局库** —— dagre / elkjs / d3-force / cytoscape 等一律禁止。分层布局自研，这是本项目主要技术亮点。
3. **不引 AG-UI 官方 SDK** —— `@ag-ui/*` 禁止安装，协议解析层自研（≤300 行）。
4. **禁止自作主张加功能** —— 不在任务卡范围内的功能，一律不做。宁可少做，不可多做。
5. **禁止为跑通而绕过类型** —— 不使用 `any` 强转、`@ts-ignore`、`as unknown as X` 来掩盖设计问题。类型报错说明设计有问题，提出来。
6. **不写 placeholder / TODO 占位** —— 要么实现，要么在任务卡里标 BLOCKER。

## 7. 决策优先级

当需求冲突时，按此顺序取舍：

1. **技术亮点可讲性**（这是简历项目，能讲出深度 > 功能齐全）
2. 核心正确性（因果推导不能错）
3. 交互性能
4. 视觉美观
5. 功能覆盖面

> 推论：宁可只支持 3 个故障剧本但每个都讲得透，也不要做 20 个剧本但都浅。

## 8. 事件源策略

**分两阶段，接口先行**：

```
TraceSource (接口)
├── SimulatedSource   ← Phase 0/1 使用：剧本驱动的可编程假运行时
└── DecisionCourtSource ← Phase 2：接 E:\Code\DecisionCourt-new 的真实后端
```

**为什么先做 mock 而非直接接真实后端**：
1. 本项目价值在可视化与交互层，被观测对象只是数据源。绑定 16500 行重写进度会带来停摆风险。
2. 真实 Agent 非确定性，无法稳定复现故障场景；可编程假运行时能精确注入故障，面试 demo 每次稳定。
3. mock 源意味着项目可纯静态部署——**简历上的链接别人点开就能看**，不需要本地起后端。这条最重要。
