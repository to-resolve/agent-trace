### 第一部分：阻塞项（必做）

#### B1 · 删除 `src/__probe7.test.ts`

临时探针文件，**未列入 T7 变更清单**，导致：

```
npm run tsc  → exit 2（3 处类型错误，全在该文件）
npm test     → 11 文件 / 147 测试 / 1 failed（提交材料声称 exit 0 / 144 passed）
```

根因：探针把未转换的 `ScenarioEvent` 直接喂给 `applyEvent`，绕过 `SimulatedSource` 的时间基准转换，`entity.time` 为 `undefined`。产品代码没问题（剔除后 144 passed 与材料一致）。

- [ ] 删除该文件
- [ ] 重新跑 `tsc` / `test` / `coverage`，**贴真实输出**

#### B2 · 三项核心验证补进正式测试（干净数据）

删除探针后，T7 的三个核心正确性断言**全部消失**。用干净数据（`SimulatedSource` 转换后的真实事件，或 `synth` 生成器）重写进正式测试文件：

- [ ] **选中 → 取消 → 边全部归零**：`buildScene(graph, layout, spanId, v)` 后 `buildScene(graph, scene.layout, null, v)`，断言 `layout.edges.every(e => e.state === 'normal')`。这是执行者自己发现并修复的 bug（选中→点空白→边永久高亮），**目前零自动化守卫**
- [ ] **边级增量对象复用**：未受影响的边引用相等（`toBe`）；受影响的边重建后几何正确
- [ ] **10k 规模边一致性**：回放后 `layout.edges` 与 `graph.edges` 按 `(fromSpanId, toSpanId, viaEntityId)` 三元组双向无差（正式套件里当前只有 4 节点规模）

#### B3 · bench 方法学修正（裁决 6）

**问题**：提交材料（Node 24.18.1 / V8 13.6）M2 p95 = 1.567ms 达标；指挥者复现（Node 22.22.2 / V8 12.4）两次实测 2.455 / 2.317ms，**稳定超 2ms 验收线**。差约 50%，CPU 相同。结论：**「p95 < 2ms」是环境的函数，不是代码的客观属性。**

- [ ] **环境指纹**：bench 输出表头加 Node 版本、V8 版本、CPU、平台
- [ ] **预热**：丢弃前 10% 轮次
- [ ] **多轮取中位数**：≥ 3 轮，单轮结果不作为结论
- [ ] **采样口径声明**：当前 27717 个样本混合了「小图阶段」（图从 0 增长）与「满图阶段」两个不同总体，p50 被系统性稀释。要么改为固定图规模反复触发（只测满图单事件成本），要么明确声明测的是回放全程分布并**只报 p95/p99**
- [ ] **降低计时开销占比**：每事件 6 次 `performance.now()`，在 M2 的 0.24ms 绝对值上占比可观。改批量计时（外层计时求差）或扣除基线
- [ ] **两个 Node 版本各跑一次**：Node 22 与 Node 24 的绝对数字都进提交材料
- [ ] **验收标准改为相对基线**：同环境下 M2 p95 相对 T7 优化前基线（4.05ms）的改善率。绝对毫秒数仅作标注环境的参考值
- [ ] `package.json` 加 `engines` 声明推荐 Node 版本

### 第二部分：建议项（必做，成本低）

- [ ] **S1**：`layout.ts` 文件头补注释——`computeLayering` 的**递归深度上界 = affected 子图内沿入边的未 memo 链长**。当前注释只论证了环安全，没论证栈深。构造反例：`A→B` 且 `A→C₁→…→C_k→B`，当 B 先于 C 链入 affected 时深度达 k+1。当前调用约定下实测 1–2，**不要求改代码**，只要求把约束写清楚

## 审查流程

```
执行者提交 → 架构负责人审查代码 → 输出 docs/reviews/T{n}-审查.md
                                      ├─ 通过 → 发布下一批任务卡，计划可能调整
                                      └─ 打回 → 问题清单 + 修改要求，重做后再审
```

审查关注点（按优先级）：红线是否违反 → 契约是否一致 → 设计是否走偏 → 实现质量 → 代码风格。
审查结论会写进 `docs/reviews/`，并可能**回头修订 `01` / `02` 文档**——发现契约本身有问题时，改文档而不是将就代码。
